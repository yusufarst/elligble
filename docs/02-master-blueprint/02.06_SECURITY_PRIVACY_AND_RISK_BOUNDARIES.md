# MB-06 — Security, Privacy & Risk Boundaries

**Status:** LOCKED v1.0.0  
**Last Updated:** 2026-08-16  

## 1. Document Authority, Status, Purpose, and Scope

This document (MB-06) operates strictly under the canonical Decision Hierarchy (`docs/00-governance/00.02_DECISION_HIERARCHY.md`) and the Agent Context Rules (`docs/00-governance/00.04_AGENT_CONTEXT_RULES.md`).

The canonical purpose of MB-06 is to define **conceptual security zones and privacy controls**. It establishes the logical boundaries, risk categorizations, and privacy defaults that govern ELLIGBLE. 

MB-06 dictates **WHAT** security, privacy, and risk boundaries must conceptually hold. It explicitly does **NOT** define **HOW** these are technically implemented. Technical IAM architecture, encryption algorithms, database schemas, Row-Level Security (RLS), OAuth/OIDC protocols, Web Application Firewalls (WAF), and SIEM implementations are deferred to Architecture.

## 2. Security & Trust Boundary Principles

ELLIGBLE relies on strict conceptual boundaries to govern access and trust:

*   **Platform vs. Tenant Boundary:** Platform operations govern shared infrastructure and capabilities, but Tenant data remains academically and operationally isolated.
*   **Organization ≠ Tenant:** An Organization may span multiple Tenants, but the security and privacy boundary for academic data is the Tenant.
*   **Person ≠ User Account ≠ Membership:** A Person is a continuous human identity. A User Account is a credentialed lifecycle state. Membership represents a contextual, time-bound authorization scope within a specific Organization/Tenant.
*   **Role/Base Access ≠ Assignment:** Base access (e.g., standard Staff) does not automatically grant contextual privileges. Assignments (e.g., teaching a specific Rombel) authorize contextual access.
*   **Teacher ≠ Teaching Assignment:** A person holds the "Teacher" role, but their authorization to view or grade student data is strictly bounded by their active Teaching Assignments.
*   **Teacher ≠ Proctor:** Being a Teacher does not automatically grant unrestricted proctoring visibility over all Secure Assessments.
*   **Partner Organization ≠ Partner Staff:** Authorization applies contextually to the specific staff member, not globally across the entire Partner entity.

Access across ELLIGBLE must be **purpose-limited**, enforce **minimum necessary exposure**, and protect **privileged/high-risk actions** from unauthorized execution. Downstream consumption of data does not transfer authoritative ownership or grant unrestricted upstream visibility.

## 3. Privacy Default Boundaries

ELLIGBLE enforces the following privacy-default rules based on canonical product decisions:

*   **Tenant Isolation:** Academic and operational data defaults to strict Tenant isolation.
*   **Contextual Access:** Information is exposed only to actors with an explicit, authorized context (e.g., an active assignment or confirmed connection).
*   **Minimum Necessary Exposure:** Systems must present only the specific data required for the task. Sensitive information (e.g., Care cases, early warnings) must not become broadly visible merely because it exists.
*   **Historical Continuity Limits:** Maintaining historical identity continuity does not imply perpetual access to a user's data after they leave a context.
*   **No Unrestricted Student Search:** Partners cannot arbitrarily browse the global student database. Talent discovery remains purpose-limited and bounded by consent/authorization (searchable fields remain PROVISIONAL).
*   **No Student-Data Marketplace:** The sale of the student database is strictly PROHIBITED.
*   **No Continuous-Video-Surveillance Baseline:** Always-on surveillance is excluded from the baseline product.
*   **Private by Default:** Public exposure is never the default for student profiles or passports.

## 4. Conceptual Risk Categorization

MB-06 categorizes risks conceptually based on canonical risk surfaces. This is not a numerical scoring taxonomy or ML detection schema.

| Risk Category | Protected Context / Asset | Type of Risk | Evidence / Accountability Boundary | Privacy-Default Implication |
| :--- | :--- | :--- | :--- | :--- |
| **Identity / Access Risk** | Person, Account, Membership | Unauthorized access, privilege escalation, account takeover | Identity Core; auth events | Access defaults to least-privilege context |
| **Cross-Tenant Data Risk** | Tenant academic/operational data | Data leakage across Tenant boundaries | Tenant boundaries; Platform IAM | Strict data isolation |
| **Assessment Integrity Risk** | Exam questions, active Sessions, attempt validity | Cheating, unauthorized exposure, content theft | Secure Assessment monitoring / proctor decisions | Monitoring scoped strictly to exam context |
| **Care Safeguarding Risk** | Care cases, counseling notes | Unauthorized exposure of highly sensitive student welfare data | Care domain; referral authorizations | Maximum privacy; isolated from broad Track |
| **Passport/Partner Privacy Risk**| Endorsed Passports, Applications | Inappropriate Talent Discovery exposure or profile scraping | Path / Connect domains; consent logs | Opt-in / authorization-aware exposure only |
| **Platform Incident Risk** | System availability, overarching security | Outages, systemic breaches, DDoS | Platform Operations; SIEM/Audit | Transparency to Tenants without exposing PII |
| **AI/Biometric Risk** | Biometric data, automated inferences | Invasive surveillance, bias, automated unauthorized decisions | AI Subsystem (FUTURE); opt-in logs | Strictly optional; no baseline dependencies |

## 5. Identity & Access Security

*   **Account State vs. Person Continuity:** Deactivating a User Account secures the access credential but does not destroy the continuous Person identity.
*   **Membership-Scoped Access:** Authorization is heavily dependent on the context of the user's active Membership within a Tenant.
*   **Privilege & Break-Glass:** High-risk actions require elevated authorization. Emergency intervention capabilities are necessary, though the specific **Break-Glass Policy** remains PROVISIONAL.
*   **Authentication & Security Presets:** **Full Authentication Policy** and **Security Preset Composition** (the mechanisms for applying baseline security levels to Tenants) remain PROVISIONAL. 

*Note: Passwords, MFA protocols, OAuth, token schemas, and RBAC matrices are deferred to Architecture.*

## 6. Secure Assessment Security & Integrity

Secure Assessment integrity is a mission-critical boundary.

*   **Student ≠ Exam Participant ≠ Exam Attempt ≠ Exam Session:** Security boundaries must differentiate the user, their authorized participation context, their submitted answers, and the active technical connection.
*   **Assessment Type ≠ Exam Instance:** Security rules apply to the specific instance and context of the exam being delivered.
*   **Anti-Cheating Requirement:** Preserving exam integrity is a LOCKED requirement. However, the specific **Anti-Cheating Platform Capability** and **Split-Screen Detailed Detection** heuristics remain PROVISIONAL.
*   **Proctoring:** The Teacher who created the exam may have scoped monitoring access, but explicit Proctor roles exist for institutional/high-stakes contexts.
*   **AI/Biometrics:** **Face Recognition / Biometric Proctoring** and **Advanced AI Proctoring** are FUTURE capabilities. They must not form the required baseline.

## 7. Risk Signal, Incident & Decision Semantics

MB-06 enforces strict semantic boundaries to prevent automated systems from making unaccountable disciplinary decisions.

*   **Violation Event ≠ Risk Signal ≠ Incident ≠ Cheating Decision**
*   **Signals are not Proof:** A risk signal (e.g., losing focus on the exam window) is evidence, not a final disciplinary conclusion. Network, IP, or location data alone does not constitute proof of cheating.
*   **Accountability:** Monitoring evidence must be interpreted by an authorized human actor (or governed policy) to become a finalized Cheating Decision.

## 8. Track & Care Safeguarding & Privacy

A severe privacy boundary exists between generalized tracking and sensitive student care.

*   **Early Warning = Track Signal.**
*   **Early Warning ≠ Care Case:** Track generates derived insights. It does not automatically create or mutate a highly sensitive Care Case.
*   **Care Authorization:** A Care Case only exists via authorized referral or intake.
*   **Minimum Necessary Referral:** Only essential context crosses from Track to Care. Detailed Care notes never leak back to Track.
*   **Open Governance:** **Early Warning Rules**, **Care Safeguarding Rules**, and the overarching **Data Classification + Consent Governance** model remain OPEN.

## 9. Passport & Path Security & Privacy

*   **Profile ≠ Portfolio ≠ Passport:** Unverified Profile data cannot silently bypass security controls to become trusted, endorsed Passport evidence.
*   **Passport Trust:** The Passport is governed evidence. The specific **Passport Trust-Level Rules** (how trust is algorithmically or procedurally quantified) remain PROVISIONAL.
*   **Path Consumption:** Path consumes authorized data from the Passport to calculate goals and targets, but it cannot mutate the source Passport truth.
*   **Goal ≠ Target ≠ Action**
*   **Readiness ≠ Eligibility**
*   **Relevant ≠ Eligible ≠ Recommended**

## 10. Partner Access & Talent Discovery

*   **Purpose-Limited Exposure:** Partner access is strictly authorization-aware and consent-aware where applicable.
*   **Opportunity ≠ Application ≠ Verified Connection ≠ Outcome:** These represent distinct stages with escalating security/privacy thresholds. An Opportunity does not grant the Partner access to the student; a Verified Connection does (with scoped communication).
*   **Talent Discovery:** Unrestricted browsing of the student population is prohibited. The specific **Talent Discovery Searchable Fields** remain PROVISIONAL.

## 11. Support, Security & Platform Incident Boundary

*   **Support Case ≠ Platform Incident:** A user-reported issue (Support Case) is distinct from a systemic risk or breach (Platform Incident).
*   **Workflow Distinctions:** Support workflows, security/privacy concerns, risk signals, and platform incidents require distinct accountability tracking and must not be conflated in data exposure.

## 12. Audit & Accountability

Audit is a shared platform capability providing essential accountability. 

*   **Provenance:** High-risk actions, security decisions, and privacy overrides must retain conceptual provenance (who did what, when, and under what authority).
*   **Attribution:** Sensitive access must be attributable.
*   *Note: Technical audit log schemas, SIEM integration, and event sourcing are deferred to Architecture.*

## 13. Fixed Negative Security & Privacy Decisions

MB-06 explicitly preserves canonical negative decisions that establish structural privacy limits:

*   **DROP:** Social Feed as Primary Direction (limits broad privacy exposure).
*   **DROP:** Follower / Friend Graph (prevents unrestricted social networking risks).
*   **DROP:** SUPER_ADMIN Omnipotent Role (prevents unaccountable global access; replaced conceptually by governed PLATFORM_OWNER / PLATFORM_STAFF roles).
*   **DROP:** Continuous Video Surveillance Baseline (limits baseline privacy invasion).
*   **PROHIBITED:** Student Database Sale (absolute governance boundary).

## 14. Future, AI & Biometric Risk

AI capabilities remain explicitly **FUTURE / OPTIONAL / NON-BLOCKING**. No paid AI dependency may become part of the required security baseline.

The following capabilities are acknowledged for future risk categorization but are excluded from baseline design:
*   Face Recognition / Biometric Proctoring
*   Advanced AI Proctoring
*   Advanced Trust & Safety Console
*   Public Alumni Directory (requires opt-in privacy defaults)
