# ELLIGBLE Master Blueprint: MB-07 — Reliability & Failure Containment

## 1. Purpose

This document defines the conceptual reliability invariants, failure-containment boundaries, and continuity principles for the ELLIGBLE platform. It establishes WHAT must remain reliable and WHERE failures must be isolated, ensuring that outages, interruptions, or partial degradation do not silently corrupt canonical truth, forfeit critical high-stakes assessment data, or transfer data ownership inappropriately.

This document does **not** specify how infrastructure implements these boundaries (e.g., database topologies, queue implementations, retry algorithms, backup architectures, or operational incident runbooks).

---

## 2. Authoritative Truth During Failure

Building upon the MB-05 (Data Trust & Continuity Model) principle of "ONE DOMAIN OWNS THE TRUTH", the following invariants apply to platform failures, delays, or outages.

### 2.1 Ownership Is Not Transferred by Failure
A failure, network partition, or delayed cross-domain event does not silently change the authoritative owner of a data record.
- **Derived State:** Downstream/projection state does not silently become the new authoritative master if the source system goes offline.
- **Stale Projections:** A disconnected downstream service reading a stale projection must recognize it as a historical/cached snapshot, not live truth.

### 2.2 Unconfirmed State Must Not Fabricate Confirmed Truth
- **No Silent Guesses:** The platform must not silently guess or fabricate critical journey state during an interruption.
- **Uncertainty Must Be Visible:** A client-side or downstream representation of uncertain/pending state must not be falsely presented as confirmed, finalized success.

### 2.3 Idempotency and Duplicate Operations
- **Idempotency Bound:** Where a canonical operation is defined as unique/idempotent (e.g., Exam Submission), duplicate deliveries or user retries (caused by network lag/clicks) must not create un-governed duplicate canonical outcomes.
- **Authorization Limit:** A retry must not bypass the original access and authorization rules.

## 3. Mission-Critical Secure Assessment Continuity

Secure Assessment is ELLIGBLE's highest-priority, flagship domain. An active exam is a high-stakes, highly protected operational state. 

### 3.1 Zero Lost Answers Invariant
Under expected recoverable failure scenarios (e.g., network drop, browser crash, device battery loss), the platform must prioritize the preservation of student answers.
- **Accepted vs Pending:** Interruption must not silently discard answer state that the server has already acknowledged.
- **Autosave Expectation:** A continuous/periodic answer-saving model is conceptually mandatory to limit data loss windows. (Exact intervals and storage mechanics are deferred to Architecture.)
- **Recovery Integrity:** Recovery workflows must preserve existing answers and must not silently overwrite newer authoritative truth with older local cache data.

### 3.2 Authoritative Timer
- **Server Authority:** The authoritative exam timer resides server-side or is governed by server-side policy.
- **Client Dependency:** The student device clock must not act as the authoritative source of truth.
- **Interruption Timing:** Reconnection after a network failure does not reset the timer duration arbitrarily; time accounting follows explicit exam policy (continue/pause/grace rules).

### 3.3 Idempotent Submission
- **Duplicate Protection:** Repeated submission attempts (due to lag or retry) must resolve to exactly one governed submission outcome.
- **Irreversibility:** A successfully submitted Exam Attempt must not silently return to an ambiguous active state due to a delayed synchronization retry.

### 3.4 Reconnect ≠ Retake
An Exam Attempt is the student's governed assessment opportunity. An Exam Session is the technical runtime connection.
- **Seamless Continuation:** Reconnecting after a technical session loss (e.g., closing the tab, transferring devices) must attach to the *same* valid Exam Attempt if authorized by policy.
- **No Automatic Retake:** A session interruption must not silently create a new Exam Attempt (a Retake).
- **Snapshot Stability:** The Exam Question Snapshot and rules must remain stable during the Attempt, even across reconnections.

## 4. Partial Failure and Dependency Isolation

ELLIGBLE operates as a modular monolith with logical domain boundaries. A localized failure must not cascade into an unrelated domain.

### 4.1 Assessment Dependency Priority
During active exams, Secure Assessment requires a strict set of **MUST HAVE** dependencies:
- Identity / Authentication
- Assessment Core
- Answer Persistence
- Timer Authority
- Submission
- Essential Security

If a dependency is **CAN DEGRADE** (e.g., Notification, Search, Messaging, Track, Insight, Partner, Billing), its failure or absence must not destabilize, interrupt, or corrupt an active Secure Assessment.

### 4.2 Failure Isolation Boundaries
- **Track Down ≠ Exam Down:** A failure in the Track domain (e.g., early warning signal processing) does not stop an active exam.
- **Billing Down ≠ Active Exam Down:** A subscription/commercial failure does not abort an in-progress exam attempt.
- **Partner Down ≠ Academic Core Down:** A failure in a third-party Partner API does not prevent school Academic Core operations.
- **Path Down ≠ Passport Down:** Path analysis failure does not rewrite or lock the student's underlying Passport truth.

### 4.3 Degraded Mode and Optional Capabilities
- **Non-Blocking Features:** AI capabilities and non-critical analytical pipelines are FUTURE / OPTIONAL / NON-BLOCKING. Their failure or absence must result in graceful degradation, allowing core workflows to continue manually or without enhancement.
- **No Ownership Transfer:** Operating in degraded mode does not silently change canonical domain ownership or authorization rules.

## 5. Domain Failure Containment

### 5.1 Identity & Tenant Containment
- **Tenant Isolation:** A failure or performance degradation must not silently weaken cross-tenant boundaries.
- **Authentication Failure:** An inability to verify credentials/tokens must default to denial, not authorization bypass. Membership and Assignment context remain the authoritative bounds for access, even during failure.

### 5.2 Track & Care Containment
- **Care Safeguarding:** Care Cases require authorized referral/intake. A delayed or duplicate Track signal (e.g., Early Warning) must not autonomously fabricate a Care Case.
- **Referral Failure:** A failed referral network request must not silently imply successful Care intake.
- **Privacy Protection:** A failure in the Care domain must not broaden visibility or leak sensitive Case information into unrelated domains.

### 5.3 Passport, Application, and Ecosystem
- **Snapshot Integrity:** A live Passport change or downstream integration retry must not rewrite a historical Application Snapshot.
- **Lifecycle Transition:** Partner dependency outages or repeated retry attempts must not silently force a state transition (e.g., Application → Verified Connection, or Verified Connection → Outcome) without explicit canonical authority.
- **Uncertain Outcomes:** An uncertain or timed-out request to a Partner must remain an unresolved state, not a confirmed Verified Connection.

### 5.4 Support vs. Incident Boundary
- **User-Facing Failure:** A localized domain error or degraded capability should be surfaced safely to the user (and may generate a Support Case).
- **Platform Incident:** Widespread outage, data loss risk, or systemic degradation constitutes a Platform Incident.
- **Security/Privacy Incident:** MB-06 governs data breaches and security compromises. Reliability tools must respect those incident classifications.

---

## 6. Recovery and Reconciliation Boundaries

When components reconnect or recover from a failure, they must reconcile state safely.

### 6.1 Re-Establishing Truth
- Recovery and reconciliation workflows must preserve authoritative ownership (MB-05).
- Reconciliation must not silently invent state that was never authorized or bypass access/security boundaries.
- The system must explicitly distinguish between unresolved/uncertain state and confirmed state until authoritative resolution is achieved.

### 6.2 Implementation Deferrals (Backup and Incident Readiness)
- **Backup/Restore:** The platform must support recovering canonical truth after a catastrophic failure. However, exact backup technologies, RPO/RTO constraints, and Disaster Recovery topologies are deferred to Operations/Architecture.
- **Incident Readiness:** While the platform must maintain a conceptual boundary for incident detection, the specific SIEM, monitoring stacks, alerting tools, and runbooks are deferred to Operations/Architecture.

## 7. Failure-Containment Matrix

*This matrix is conceptual and describes what must hold during a failure, not how the system achieves it technically.*

| Context / Journey | Authoritative Owner | Interruption / Failure Scenario | Must Preserve (Invariant) | Safe Degraded Boundary | Must Not Happen |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Secure Assessment** | Assessment | Client crashes/network drops during active exam | Associated Attempt; previously acknowledged answers | Local UI shows "offline/pending" sync state | Do not auto-submit prematurely; do not delete answers; do not create Retake. |
| **Secure Assessment** | Assessment | Student retries final submission 5x due to lag | Idempotency of submission | Request pends/queues safely | Do not create duplicate canonical submission records. |
| **Assessment Timers** | Assessment | Device clock changed or offline | Server-authoritative remaining time | Client timer pauses or warns | Local device clock overrides official exam duration. |
| **Cross-Domain APIs** | Source Domain (e.g., Track) | Downstream domain (e.g., Insight) is unavailable | Source domain operation completes | Downstream async delivery retries safely | Active Exam or Academic workflow blocked by Insight outage. |
| **Care Referral** | Care (for intake) | Referral message delayed or duplicate | Care intake authorization gate | Warning: Referral delayed | Duplicate Track event silently creates multiple Care cases. |
| **Application** | Opportunity Ecosystem | Passport updates while Application is pending | Application Snapshot integrity | Current Passport differs from submitted App | Live Passport edits alter past Application truth. |
| **Ecosystem Integrations**| Partner / Opportunity | Partner API timeout | Local application state (Pending) | Workflow pauses for user | Timeout silently recorded as Verified Connection. |
| **Identity/Access** | Identity | Auth service degraded/timeout | Default deny access | Login unavailable | Fallback to unauthenticated guest access to core data. |
| **Optional Capabilities** | Varies | AI / Smart feature offline | Core canonical workflow | Manual process enabled | Core workflow blocked because AI cannot respond. |

## 8. Maturity & Deferred Decisions Register

To ensure clarity, the following states govern the rules within MB-07 and its downstream implementation dependencies.

### Conceptually LOCKED Invariants
The following concepts are explicitly supported and LOCKED by Discovery/Governance sources:
- **Zero Lost Answers** (Conceptual priority)
- **Server-Authoritative Timer**
- **Idempotent Submission**
- **Reconnect ≠ Retake**
- **One Domain Owns The Truth**
- **Assessment Failure Isolation Boundaries**

### OPEN
- **Care Safeguarding Rules:** Explicit operational rules around Care failure behavior (and associated legal/privacy obligations) remain OPEN.

### PROVISIONAL
- **Cross-Domain FK / Event Strategy:** The exact strategy for cross-domain data consistency (foreign keys vs. event publishing) remains PROVISIONAL and is deferred to Architecture Discovery.
- **Anti-Cheating Platform Capability:** The technical limits of browser capability and detailed detection heuristics remain PROVISIONAL.

### FUTURE
- **AI Features:** All AI-driven analytics, automation, or content generation remain FUTURE / OPTIONAL / NON-BLOCKING.

### Implementation / Production Readiness Deferrals
The following are mandatory production blockers but are NOT conceptually designed within the Master Blueprint:
- **Backup + Restore Verification:** (Technology, RPO/RTO, testing)
- **Security / Incident-Response Readiness:** (Runbooks, monitoring tools)
- **Technical Zero-Lost-Answer Mechanism:** (Autosave protocols, local storage tech)
- **Assessment State Machine Implementation:** (Database transitions, exact enums)
