# MB-04 — Core Journeys & Critical Flows

**Status:** LOCKED v1.0.0
**Last Updated:** 2026-08-16

## 1. Document Authority, Status, and Scope
This document (MB-04) defines the core conceptual journeys, cross-domain handoffs, and critical flows for ELLIGBLE. It operates strictly within the boundaries established by MB-01, MB-02, and MB-03. This is a conceptual blueprint, not a UI specification, API contract, or database schema.

## 2. Source Authority and Evidence Rules
MB-04 does not define independent authority ordering. Source authority is governed exclusively by the canonical Decision Hierarchy (`docs/00-governance/00.02_DECISION_HIERARCHY.md`) and supersession rules (`docs/00-governance/00.04_AGENT_CONTEXT_RULES.md`).

A LOCKED concept must not be presented as a fully defined operational journey when its mechanics remain OPEN.

## 3. Journey Modelling Conventions
- **Concept Authority:** Differentiates the existence of a concept from its detailed rules.
- **Conceptual Abstraction:** Implementation mechanics (e.g., autosave) are abstracted into requirements (e.g., "temporary connectivity loss must not inherently cause answer loss").

## 4. Actors, Contexts, Trusted Records, and State Boundaries
Actors move through state transitions by manipulating or viewing Trusted Records, governed by strict Context. Role is not the same as active actor context. Person is not Account.

## 5. Core Conceptual Journeys and Subflows

### S-01 School/Tenant Onboarding
- **Purpose:** Establish baseline school tenant environment.
- **Primary / Supporting Actors:** Platform Owner / School Operator.
- **Actor Context:** Platform Administration.
- **Preconditions:** Authorized organization/school onboarding event.
- **Trigger:** School approval process.
- **Conceptual Steps:** Recognize Organization, establish academic-tenant boundary for SMA/sederajat, provision tenant context.
- **State Transitions:** Unrecognized -> Recognized Organization -> Active Tenant.
- **Trusted Data/Record:** Tenant Configuration Record.
- **Authorization Point:** Platform Owner approval.
- **Consent Point:** OPEN (Organizational agreement mechanics remain OPEN).
- **Cross-Domain Handoff:** Platform -> Tenant operations.
- **Interruption/Failure Paths:** Failure when organization, tenant, or authority cannot be validated.
- **Conceptual Recovery:** Resolution depends on organizational agreement/verification process.
- **Success Condition:** Initial authorized school administration context established.
- **Negative Rules:** Organization is not automatically Tenant. No implicit cross-tenant membership or operations.
- **Concept Authority:** LOCKED.
- **Evidence Type:** docs/01-discovery/02.01_TENANT_ORGANIZATION_IDENTITY_ACCESS.md
- **Detail Maturity:** OPEN (Exact provisioning mechanics remain deferred).

### S-02 Identity-to-Membership
- **Purpose:** Map a valid Person to an Academic Tenant context.
- **Primary / Supporting Actors:** Person / System / Operator.
- **Actor Context:** Identity Owner / Enrolling Member.
- **Preconditions:** Valid Person identity exists; Valid Organization and Tenant boundary exists.
- **Trigger:** Authorized enrollment/invitation/acceptance event.
- **Conceptual Steps:** Validate Person ID, explicitly authorize and accept membership within a specific Tenant.
- **State Transitions:** Registered Person -> Tenant Member.
- **Trusted Data/Record:** Membership Record.
- **Authorization Point:** Tenant enrollment authorization.
- **Consent Point:** OPEN (Consent, acceptance, or institutional mandate mechanics remain OPEN).
- **Cross-Domain Handoff:** Identity -> Membership (HD-01).
- **Interruption/Failure Paths:** Membership creation failure/interruption.
- **Conceptual Recovery:** Handled via OPEN enrollment resolution.
- **Success Condition:** Person is actively mapped as a Member of the Tenant.
- **Negative Rules:** Person ≠ User Account ≠ Membership. Organization ≠ Tenant. Person ID is the only baseline identity object crossing into Membership. Historical school data does not cross automatically into a new Membership/Tenant. No implicit cross-tenant authorization. Account activation/deactivation is distinct from Membership or Assignment activation/deactivation.
- **Concept Authority:** LOCKED.
- **Evidence Type:** docs/01-discovery/02.01_TENANT_ORGANIZATION_IDENTITY_ACCESS.md
- **Detail Maturity:** OPEN (Exact enrollment, invitation, transfer, expiry, and reactivation mechanics remain OPEN).

## 6. End-to-End Secure Assessment Critical Flow
Secure Assessment is mission-critical. Other platform functions must not degrade an active assessment.

**Entities (Distinct Concepts):**
- Assessment Type/Definition
- Exam Instance
- Question Bank Item
- Exam Question Snapshot
- Participant Assignment
- Exam Participant
- Exam Attempt
- Exam Session

**Conceptual Lifecycle & Invariants:**
- Assessment creation and authorization.
- Assignment to the correct participant context.
- Readiness/device/session checks.
- Attempt activation.
- Reconnection resumes the same valid Attempt; it must not silently create a replacement Attempt.
- Session loss must not inherently cause answer loss.
- The timer is server-authoritative.
- Duration must remain continuous across reconnect.
- Submission must be idempotent.
- A submitted Attempt must not return to an ambiguous active state.
- Scoring.
- Controlled result publication.
- Session loss does not create a new Attempt.

**Violation Event Boundary:**
- Violation Event ≠ Risk Signal ≠ Incident ≠ Cheating Decision.
- Network, IP, location, reconnect, or device change must not automatically become cheating proof.

Note: Implementation algorithms, state persistence, retry algorithms, and Assessment reliability mechanics belong to MB-07.

## 8. Journey Criticality Classification
Every core journey and the Support/Incident subflow must have an evidence-supported classification:
- **MISSION-CRITICAL:** Secure Assessment (S-04, J-02, S-05). Non-assessment workloads must not degrade active assessment.
- **TRUST-CRITICAL:** Identity & Access (J-01), Application (J-10), Passport (J-08), Care (J-06).
- **CORE:** Academic Core (J-03).
- **OPEN/DEFERRED:** Criticality classification for J-04, J-05, J-07, J-09, J-11, J-12, S-01, S-02, S-03, S-06 remain OPEN pending future discovery.

## 9. Interruption, Recovery, and Negative Journeys
**Binding Boundaries:**
- Organization ≠ Tenant.
- Person ≠ User Account ≠ Membership.
- Teacher ≠ Teaching Assignment.
- Teacher ≠ Proctor.
- Student ≠ Exam Participant ≠ Exam Attempt ≠ Exam Session.
- Violation Event ≠ Risk Signal ≠ Incident ≠ Cheating Decision.
- Student data is private by default.
- No implicit cross-tenant authorization.
- Partner has no unrestricted student search.
- Network/IP/location change is not cheating proof.
- Submitted assessment state must not become ambiguous.
- ELLIGBLE is not social media. Verified Connection is not a follower/friend graph. Unrestricted directory/student discovery is prohibited. Scoped contextual communication may exist when authorized, purpose-bound, and privacy/policy-compatible.
- Application Snapshot must not be replaced by a mutable live Passport.
- Graduation must not create a new Person.
- Talent Assurance remains FUTURE/provisional.
- Base Access ≠ Operational Assignment.
- Guardian ≠ Student.
- Partner Organization ≠ Partner Staff.
- Account deactivation/reactivation ≠ Membership deactivation/reactivation ≠ Assignment deactivation/reactivation.
- Historical school data does not automatically cross into another Membership/Tenant.
- Consent to one context does not imply consent to every downstream disclosure.
- Support Case ≠ Platform Incident.
- Assessment Definition ≠ Exam Instance.
- Question Bank Item ≠ Exam Question Snapshot.
- Relationship status ≠ Person identity status.
- Legacy SUPER_ADMIN references must not be promoted into the current canonical role model.
