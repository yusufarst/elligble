# ELLIGBLE Actor, Role & Context Map

==================================================
## 1. Purpose
==================================================

Define the conceptual actor/access model for ELLIGBLE.

Clarify:
who the Person is,

what operational assignments they hold,
and what scope/context bounds those responsibilities.

==================================================
## 3. Identity, Access & Responsibility Dimensions
==================================================

- **Person**: The actual human identity.
- **User Account**: Credential/login access.
- **Membership**: Attachment to a specific Organization or Tenant.
- **Base Access**: Broad contextual classification (e.g., SCHOOL_STAFF).
- **Operational Assignment**: Explicit operational duty (e.g., TEACHER).
- **Capability**: Conceptual permitted action.
- **Scope**: Boundaries restricting capability (e.g., subject, exam, tenant).
- **Policy / Context**: Final dynamic check (e.g., immutable state, unrelated rooms).
- **Relationship Context**: Verification between persons (e.g., GUARDIAN).
- **Lifecycle Context**: Lifecycle state of a person (e.g., ALUMNI).
- **Domain Context**: Module/subsystem execution boundary.

AUTHORIZED CONTEXT
=
Base Access
+ valid Membership
+ applicable Assignment(s)
+ required Capability
+ valid Scope
+ applicable Policy / Context

This is conceptual, NOT technical implementation.

==================================================
## 4. Identity Continuity Model
==================================================

Person is the durable human identity.
Account activation/deactivation does not create/destroy the Person.
School transfer does not create another Person.
Graduation does not create another Person.
Membership may change over time.
Assignments may change over time.
Lifecycle context may change over time.

==================================================
## 5. Base Access Map

One Person may hold multiple Base Access classifications simultaneously if they have multiple memberships or relationship contexts (e.g., SCHOOL_STAFF in one tenant and GUARDIAN in another).

| Base Access | Primary Context | What It Establishes | What It Does NOT Automatically Grant | Canonical Status |
|---|---|---|---|---|
| PLATFORM_OWNER | Highest Platform | Governance capability | Unrestricted invisible customer data access | Classification: LOCKED / Details: CONCEPTUAL |
| PLATFORM_STAFF | Internal Platform | Platform operator potential | Any specific internal action | Classification: LOCKED / Details: CONCEPTUAL |
| SCHOOL_STAFF | Academic Tenant | Staff membership in a school | Administrative or teaching rights | Classification: LOCKED / Details: CONCEPTUAL |
| STUDENT | Academic Tenant | Learning participant | Anything beyond their own context | Classification: LOCKED / Details: CONCEPTUAL |
| GUARDIAN | External / Relationship | Relationship to a student | Impersonation of the student | Classification: LOCKED / Details: CONCEPTUAL |
| ALUMNI | Post-Graduation | Former student context | Active academic rights | Classification: LOCKED / Details: CONCEPTUAL |
| PARTNER_STAFF | Partner Org | Operator for partner org | Global student search | Classification: LOCKED / Details: CONCEPTUAL |

Base Access alone does NOT grant detailed operational authority.
SUPER_ADMIN: REJECTED / NON-CANONICAL.

### PLATFORM_STAFF

Does not create one global unrestricted platform-staff role.

## 8. Teacher Context
==================================================

Teacher ≠ Teaching Assignment.
A SCHOOL_STAFF Person may receive TEACHER assignment.
Teaching authority is contextual/scoped.
Teacher does not automatically receive:
school-wide administration
Care access
Proctor authority

==================================================
## 9. Leadership & Administrative Context
==================================================

Includes assignments such as PRINCIPAL, VICE_PRINCIPAL, CURRICULUM_COORDINATOR, STUDENT_AFFAIRS_COORDINATOR, FACILITIES_COORDINATOR, PUBLIC_RELATIONS_COORDINATOR, SCHOOL_OPERATOR.
These are operational assignments/responsibilities.
Do not create permanent combinatorial roles.
Exact scope/delegation boundaries remain OPEN.

==================================================
## 10. Homeroom & Care Context
==================================================

HOMEROOM_TEACHER and COUNSELOR are distinct.
Homeroom assignment does not automatically become Care authority.
Counselor/Care access remains purpose-limited and sensitive.
Care safeguarding details: OPEN.

==================================================
## 11. Student Context
==================================================

STUDENT is a Base Access classification operating within academic membership/lifecycle context.
Student access is primarily self-centric.
Student ≠ Exam Participant.

==================================================
## 12. Guardian Relationship Context
==================================================

GUARDIAN Base Access is separate from the Guardian Relationship.
Access is relationship-scoped to specific student(s).
A Guardian account is independent from the Student account.
Guardian access must not imply Student impersonation.
Multiple guardian / multiple student relationships conceptually supported (verification policy deferred if not locked).
