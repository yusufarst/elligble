## 2. Authority and Scope

This Domain & Module Map operates under the authority of the LOCKED MB-01 Platform System Map. MB-02 does not override MB-01. Where this draft maps domains, modules, capabilities, and concepts, it does so consistently with the locked high-level bounds and canonical decisions established in prior Discovery units.

## 3. Classification Model

Conceptual classifications used in this map:

- **MAJOR PLATFORM AREA**: The highest-level logical grouping of related domains or capabilities (e.g., School Operating System).
- **DOMAIN AREA**: A logically cohesive conceptual domain with specific functional responsibility boundaries.
- **FUNCTIONAL MODULE**: A distinct conceptual functional grouping within a domain.
- **SHARED CAPABILITY**: A platform-wide functional capability that supports multiple domains without being a separate domain itself.
- **DOMAIN CONCEPT**: A primary entity or abstraction relevant to a domain's operations.
- **LIFECYCLE CONTEXT**: A state or phase in the continuous lifecycle of a core entity (e.g., Alumni).
- **STRATEGIC DIRECTION**: A validated future priority that does not yet constitute a day-one operational domain.
- **OPEN / UNRESOLVED**: An area explicitly deferred for future discovery.

Domain Area != Functional Module != Domain Concept.

## 5. Shared Platform Core

Classification: MAJOR PLATFORM AREA / shared capability layer

Shared Platform Core capabilities are shared conceptual capabilities, NOT microservices. They provide common functionality and shared truth across relevant ELLIGBLE areas.

Capabilities:
- **Identity**: Manages verified identities. Person ≠ User Account ≠ Membership.
- **Organization / Tenant**: Manages bounded organizational scopes. Organization ≠ Tenant.
- **Access Control**: Handles permissions and capability mapping. Role/Base Access ≠ Assignment.
- **Notification**: Manages actionable alerts. Reminder ≠ Notification ≠ Announcement.
- **Messaging**: Handles contextual communication. Message ≠ Support Case.
- **Search**: Context-aware discovery of resources.
- **Feedback & Support**: Role-aware help. Support ≠ Feedback, Support Case ≠ Platform Incident.
- **Audit**: System and action accountability.
- **Privacy / Trust / Security**: Shared trust mechanisms.

Do not design security controls here; MB-06 owns detailed security.

## 7. Secure Assessment

Classification: DOMAIN AREA / MISSION-CRITICAL

Primary Responsibility: High-integrity evaluation execution, isolated from non-critical module failures.

Conceptual Functional Modules:
- Question Bank
- Exam Builder
- Participant Management
- Attempt & Session Management
- Exam Runtime
- Autosave / Recovery
- Scoring
- Proctoring
- Anti-Cheating
- Evidence

Domain Concepts:
- Exam Attempt
- Exam Session

Exam Attempt ≠ Exam Session. An Attempt is one student's assessable submission opportunity. A Session is an operational runtime connection/session for that Attempt. One Attempt may span multiple Sessions (reconnect, device transfer, recovery).

Critical safeguards and distinctions:
- Student ≠ Exam Participant ≠ Exam Attempt ≠ Exam Session
- Assessment Type ≠ Exam Instance
- Question Bank Item ≠ immutable Exam Question Snapshot
- Teacher ≠ Proctor
- Violation Event ≠ Risk Signal ≠ Incident ≠ Cheating Decision
- No Lost Answers, server-authoritative timer, idempotent submission.
- Personal mobile data/hotspot allowed; school Wi-Fi not mandatory.
- Risk signal ≠ verdict. Network/IP/location is not cheating proof.

These are conceptual modules, NOT separate technical services. Do NOT design APIs, persistence, runtime topology, or technical fault tolerance.
