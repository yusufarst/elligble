# MB-09 — Delivery Sequence & Dependencies

**Status:** LOCKED v1.0.0  
**Last Updated:** 2026-08-16  

## 1. Purpose

This document (MB-09) establishes the conceptual sequence of capability delivery and defines the explicit prerequisite dependencies for the ELLIGBLE platform. It answers what conceptual foundation must exist before a subsequent capability can operate, identifies adoption-critical priorities, and outlines the production-readiness gates constraining launch.

## 2. Scope & Authority

MB-09 operates under the canonical Decision Hierarchy (`docs/00-governance/00.02_DECISION_HIERARCHY.md`) and the Agent Context Rules (`docs/00-governance/00.04_AGENT_CONTEXT_RULES.md`).

This document defines **conceptual capabilities and their dependencies**. It explicitly does **NOT** define Architecture (e.g., schemas, endpoints, exact event topologies) or Build mechanics (e.g., Build Units, sprints, engineering ticket plans).

## 3. Delivery-Sequencing Principles

*   **Dependency ≠ Chronology:** A conceptual dependency or information requirement does not automatically dictate that all upstream work must finish before downstream work can begin.
*   **Lifecycle Order ≠ Implementation Order:** An entity that exists later in a lifecycle (e.g., Outcome succeeding Verified Connection) does not automatically mandate chronological software delivery requirements.
*   **Mission-Criticality:** Secure Assessment remains the flagship adoption wedge and has priority immediately after the minimum required foundation.
*   **No Silent Upgrades:** Optional, Out-of-Baseline, and Future items must not silently enter the mandatory delivery critical path.

## 4. Dependency-Type Model

To ensure precision, MB-09 classifies dependencies across five distinct dimensions:
1.  **Product Classification:** (e.g., Baseline, Optional, Future, Out of Current Baseline).
2.  **Conceptual Capability Dependency:** Does a downstream capability rely on an upstream capability's information or services?
3.  **Entity / Lifecycle Prerequisite:** Must entity A exist before entity B can be created?
4.  **Explicit Delivery-Order Requirement:** Must the upstream system be fully delivered before downstream work can begin?
5.  **Production-Readiness / Launch Constraint:** Must an artifact or policy be finalized before production rollout?

## 5. Product Classification vs Delivery vs Readiness

MB-09 strictly preserves the separation between maturity (whether a decision is made), readiness (whether it blocks launch), and artifact status. A Production Blocker is a readiness constraint, not an automatic indication of decision maturity.

## 6. Minimum Foundation

The Minimum Conceptual Foundation must be established before dependent workflows (including Secure Assessment) can fully operate. It consists of:
*   **Identity / Auth:** Person, User Account, Authentication / Session Identity.
*   **Organization / Tenant:** Tenant boundary and Membership context.
*   **Academic Core Context:** Minimum necessary academic structure (Academic Period, Rombel, Teaching Assignment) required to authorize actions.
*   **Data Trust & Continuity Invariants:** (MB-05) Provenance and snapshot integrity rules.
*   **Reliability Invariants:** (MB-07) Failure containment boundaries.

## 7. Secure Assessment Priority

Secure Assessment is the mission-critical flagship capability. Once the Minimum Foundation is established, Secure Assessment forms the priority delivery group.

**Must-Have Dependencies for Active Exams:**
*   Identity / Auth
*   Assessment Core (Exam Instance, Session, Participant)
*   Answer Persistence
*   Timer Authority
*   Submission
*   Essential Security

**Can-Degrade Dependencies (Do Not Halt Active Exams):**
*   Search, Messaging, Track, Insight, Partner, Billing, Noncritical Notification.

## 8. Conceptual Delivery Groups / Rollout Priorities

*(Note: These are conceptual groups, NOT official project phases or sprint plans.)*

### Group A: Minimum Required Foundation
*   **Purpose:** Establish multi-tenant identity and academic authorization context.
*   **Included:** Identity Core, Organization/Tenant boundaries, Academic Core context.
*   **Hard Prerequisites:** None.
*   **Production-Readiness Gates:** Controller / Processor Legal Allocation, Authentication / Security Policy, Data Classification + Consent Governance.

### Group B: Secure Assessment Priority
*   **Purpose:** Deliver the mission-critical exam platform.
*   **Included:** Assessment Core, Answer Persistence, Timer, Submission, Essential Security.
*   **Hard Prerequisites:** Minimum Required Foundation.
*   **Production-Readiness Gates:** Assessment Capability Testing, Zero-Lost-Answer Verification, Security / Incident-Response Readiness.

### Group C: Tracking & Educational Journeys
*   **Purpose:** Provide academic progress visibility and optional learning context.
*   **Included:** Track, Learn (OPTIONAL).
*   **Conceptual Dependencies:** Track depends on Assessment and Academic Core. Learn depends on Academic Core.

### Group D: Identity Portability & Discovery
*   **Purpose:** Support verified credentials and opportunity mapping.
*   **Included:** Passport, Path, Opportunity, Application, Verified Connection, Outcome.
*   **Conceptual Dependencies:** Passport depends on Track/Assess context. Path depends on Passport and Opportunity. Application depends on Opportunity.

### Group E: Safeguarding & Care
*   **Purpose:** Secure management of sensitive student welfare referrals.
*   **Included:** Care Case management.
*   **Conceptual Dependencies:** Care conditionally receives minimum-necessary signals from Track.
*   **Production-Readiness Gates:** Care Safeguarding Policy (where Care launches).

## 9. Cross-Domain Dependency Map

*   **Academic Core** depends on **Identity / Tenant**.
*   **Assessment** depends on **Academic Core**.
*   **Track** depends on **Assessment** (and **Learn** where Learn exists).
*   **Care** depends conceptually on **Track** (for authorized referrals).
*   **Passport** depends conceptually on **Track** and **Assessment** (for approved records).
*   **Path** depends conceptually on **Passport** (for context) and **Opportunity** (for exploration).
*   **Opportunity** depends conceptually on **Passport** (consumes Application Snapshot).

## 10. Lifecycle Dependencies That Do Not Establish Delivery Chronology

The following represent Lifecycle/Instance Prerequisites and Conceptual Capability Dependencies, but strict sequential delivery order is **NOT ESTABLISHED**, and their development may possess parallel eligibility:

*   **Passport → Path:** Path conceptually consumes Passport, but delivery order is not strictly mandated.
*   **Passport → Opportunity:** Opportunity conditionally consumes a Passport Snapshot upon application, but full Passport delivery is not an automatic prerequisite for Opportunity capabilities.
*   **Opportunity → Path:** Path consumes Opportunity information for exploration, but strict chronological delivery sequence is not mandated.
*   **Opportunity → Application:** An Application conceptually requires an Opportunity for its lifecycle instance, but their capabilities may be developed and delivered in parallel.
*   **Application → Verified Connection:** A Verified Connection conceptually requires a preceding Application for its lifecycle instance, but their capabilities may be developed in parallel without automatic transition.
*   **Verified Connection → Outcome:** An Outcome conceptually requires a preceding Verified Connection for its lifecycle instance, but their capabilities may be developed in parallel without automatic transition.

## 11. Production-Readiness Gates

The following items are explicit Production Blockers that must be resolved prior to launch, irrespective of their decision maturity (which may be OPEN or PROVISIONAL):
*   Controller / Processor Legal Allocation
*   Final Retention Periods / Retention Matrix
*   Required DPIA
*   Full Authentication Policy / Security Policy
*   Permission Matrix
*   Assessment Capability Testing
*   Zero-Lost-Answer Verification
*   Care Safeguarding Policy (where Care launches)
*   Partner Verification / Moderation Policy (where Partner launches)
*   Data Classification + Consent Governance
*   Backup + Restore Verification
*   Security / Incident-Response Readiness

## 12. Optional / Future / Out-of-Baseline Constraints

The following capabilities carry explicit product classifications and must not silently become mandatory baseline dependencies:
*   **Learn:** OPTIONAL
*   **General school timetable:** OUT OF CURRENT BASELINE
*   **General school attendance:** OUT OF CURRENT BASELINE
*   **Public Alumni Directory:** FUTURE
*   **Standardized ELLIGBLE Assessment:** FUTURE
*   **Face Recognition / Biometric Proctoring:** FUTURE
*   **Advanced AI Proctoring:** FUTURE
*   **Native Android/iOS/iPadOS Apps:** FUTURE
*   **All AI Capabilities:** FUTURE / OPTIONAL / NON-BLOCKING

## 13. Cross-Cutting Capability Treatment

Capabilities such as Notification, Messaging, Search, Feedback & Support, Audit, Privacy, Insight, and Billing are **Shared Cross-Cutting Capabilities**. 
Being cross-cutting does not automatically grant them Baseline product classification. Their explicit status will be governed by MB-10. During an active exam, capabilities like Search, Messaging, and Insight are classified as **Active-Exam Can-Degrade Dependencies**.

## 14. Parallel / Sequential Precision

*   "Downstream consumes upstream truth" does NOT automatically mean all downstream work must wait until all upstream work is complete.
*   Chronological delivery requirements are strictly limited to those explicitly sourced in canonical evidence. Lifecycle ordering does not prevent parallel technical implementation.

## 15. Architecture & Build Deferrals

MB-09 explicitly defers:
*   **Architecture:** Database schemas, ERDs, APIs, endpoints, service-call patterns, foreign keys, event buses, physical topologies, and the exact cross-domain FK/Event strategy.
*   **Build:** Build Units, sprint plans, ticket execution sequences, epics, timeline schedules, or developer assignments.

## 16. Later Master Blueprint Unit Boundaries

MB-09 does not perform the comprehensive item-by-item product classification matrix (which is reserved for MB-10: Baseline, Future & Exclusions), does not perform requirement traceability (MB-11), and does not authorize final Master Blueprint exit (MB-12).

## 17. Prohibited Interpretations / MUST NOT HAPPEN

*   Dependency direction MUST NOT be mistaken for implementation order.
*   Lifecycle ordering MUST NOT be mistaken for rollout chronology.
*   Unsupported parallelism MUST NOT be asserted.
*   A Production Blocker MUST NOT be treated automatically as indicating MISSING decision maturity.
*   A MISSING artifact MUST NOT be treated automatically as resolving a decision maturity of OPEN/PROVISIONAL.
*   FUTURE items MUST NOT enter the baseline critical path.
*   OUT-OF-BASELINE items MUST NOT be scheduled into a normal later rollout wave.
*   Learn MUST NOT become mandatory for Track or Secure Assessment.
*   A Track signal MUST NOT automatically create a Care Case.
*   The Passport → Opportunity contract MUST NOT be removed or reversed.
*   The Opportunity → Path contract MUST NOT be reversed into Path → Opportunity.
*   Application MUST NOT automatically create a Verified Connection.
*   Verified Connection MUST NOT automatically create an Outcome.
*   A cross-cutting capability MUST NOT be declared Baseline merely because it is shared.
*   MB-09 MUST NOT authorize Architecture or Build execution.

## 18. Open / Provisional / Future / Readiness Register Impact

*   **Data Classification + Consent Governance:** Remains OPEN maturity, MISSING artifact, PRODUCTION BLOCKER.
*   **Full Authentication Policy:** Remains PROVISIONAL maturity, DISCOVERY artifact, PRODUCTION BLOCKER readiness.
*   **Cross-Domain FK / Event Strategy:** Remains PROVISIONAL maturity.
*   **Care Safeguarding Rules:** Remains OPEN maturity, PRODUCTION BLOCKER readiness (where Care launches).

## 19. Draft Verification Summary

This document accurately captures the canonical dependency directions, isolates lifecycle prerequisites from delivery chronology, respects established production blockers, and explicitly preserves the boundaries preventing premature Architecture or Build definition.
