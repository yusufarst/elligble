# MB-08 — Cross-Domain Contracts & Integrations

**Status:** LOCKED v1.0.0  
**Last Updated:** 2026-08-16  

## 1. Purpose / Scope

This document defines conceptual cross-domain responsibilities, information/capability exchange, ownership boundaries, and dependencies for the ELLIGBLE platform.

It is strictly a conceptual contract outlining WHICH domains own data, WHAT information or capability is exchanged, and WHICH boundaries must be maintained. It explicitly does NOT define technical integration patterns, payload schemas, event buses, or exact FK/event implementation strategies.

## 2. Canonical Contract Principles

ELLIGBLE relies on strict evidence-supported principles for all cross-domain relationships:
*   **ONE DOMAIN OWNS THE TRUTH:** Each piece of canonical truth is owned by exactly one domain.
*   **Consumption Does Not Transfer Ownership:** A domain may consume data from another, but that consumption does not transfer authoritative ownership of the source data to the consumer.
*   **No Silent Mutation:** A domain must not silently mutate another domain's canonical truth.
*   **Snapshot Authority Preserved:** Derived, projected, or historical snapshot data does not silently become source authority.

## 3. Information vs Capability vs Ownership

Cross-domain interactions fall into two conceptual categories:

*   **Information Exchange:** A consumer domain receives or views information needed for an authorized purpose. The source domain retains full authoritative ownership of that truth.
*   **Capability Request:** A requester domain asks the owning domain to perform an authorized lifecycle action. The canonical lifecycle transition occurs only under the owning domain's authority.

## 4. Domain Ownership / Consumer Model

For any cross-domain integration to exist, the following model applies:
*   **Owner / Source Domain:** Holds authoritative truth.
*   **Consumer / Requester Domain:** Receives information or requests capability.
*   **Dependency Direction:** Identifies who depends on whom for what purpose.

## 5. Dependency Direction

Dependency means a consumer requires information or a capability from an owner. It does NOT mean ownership is shared. A consumer dependency on an owner does not imply the owner requires the consumer to be available, unless a reciprocal canonical requirement exists. 

## 6. Identity/Tenant/Academic/Assessment Boundaries

*   **Person ≠ User Account ≠ Membership:** A consuming domain may rely on this contextual identity information but does not become the owner of Identity or Tenant truth.
*   **Organization ≠ Tenant:** Integrations must respect Tenant isolation boundaries.
*   **Role/Base Access ≠ Assignment:** Integrations must rely on authorized assignment contexts.
*   **Teacher ≠ Teaching Assignment ≠ Proctor:** Contextual rules govern Secure Assessment interaction.

## 7. Secure Assessment Cross-Domain Boundaries

Secure Assessment is a mission-critical domain. 
*   **Participant ≠ Attempt ≠ Session:** Assessment owns Attempt and Session truth.
*   **Question Bank Item ≠ Immutable Exam Question Snapshot.**
*   No other domain (Track, Insight, Partner, Support) may become the owner of Assessment Attempt truth, answer truth, or submission truth.
*   **Violation Event ≠ Risk Signal ≠ Incident ≠ Cheating Decision:** A cross-domain consumer (e.g., Track) of assessment risk signals must not silently convert them into final cheating conclusions.

## 8. Track/Care Boundary

*   **Early Warning = Track Signal.**
*   **Early Warning ≠ Care Case.**
*   Track may provide the minimum necessary authorized referral/signal context to Care.
*   Care strictly owns the Care Case after a valid authorized intake.
*   Track must NOT directly create Care canonical truth merely because a signal exists.
*   Care must NOT treat every Track warning as automatic intake.

## 9. Passport/Path/Application Boundary

*   **Profile ≠ Portfolio ≠ Passport.**
*   **Goal ≠ Target ≠ Action.**
*   **Readiness ≠ Eligibility.**
*   **Relevant ≠ Eligible ≠ Recommended.**
*   Passport owns governed/trusted Passport truth.
*   Path may consume authorized relevant Passport context for exploration and planning.
*   Path does NOT own Passport truth, cannot rewrite Passport truth, and cannot turn readiness or recommendation into canonical eligibility.

## 10. Partner/Opportunity/Application/Connection/Outcome Boundary

*   **Partner Organization ≠ Partner Staff:** Integrations must respect specific staff authorization limits.
*   **Opportunity ≠ Application ≠ Verified Connection ≠ Outcome:** Each stage is conceptually distinct.
*   Path consumes Opportunity information for planning but must not become the owner of Application lifecycle truth.
*   No retry or exchange may silently cause an Application to become a Verified Connection, or a Verified Connection to become an Outcome.
*   Partner access is purpose-limited and must never enable unrestricted student search.

## 11. Support/Incident Boundary

*   **Support Case ≠ Platform Incident:** Distinctions must be preserved.
*   A source domain may provide minimum necessary diagnostic information to Support where authorized.
*   Support owns Support Case truth.
*   Support does NOT automatically own academic truth, Assessment truth, Passport truth, Care truth, or Partner truth.

## 12. Projection/Snapshot/Derived Data Boundary

*   Explicit distinctions remain between Canonical Source Truth, Projection, Derived Value, Historical Snapshot, and Application Snapshot.
*   An Application Snapshot represents a historical context from Passport. Later live Passport changes do NOT silently rewrite that historical application truth.
*   A stale projection consumed by a downstream domain must not authorize that consumer to rewrite upstream truth.

## 13. Security/Privacy Constraints

Every conceptual cross-domain interaction must preserve:
*   Tenant isolation.
*   Contextual authorization.
*   Purpose limitation.
*   Minimum necessary exposure.
*   Privacy-default boundaries (e.g., Care data isolation).
*   Risk semantics.

Cross-domain dependency does not authorize broader visibility, nor does a failure authorize bypass.

## 14. Reliability/Failure Constraints

Every conceptual cross-domain dependency must preserve MB-07 boundaries:
*   Failure isolation.
*   Authoritative truth during failure (no ownership transfer during outage).
*   Safe degraded boundaries.
*   Optional/noncritical capability failure must not destabilize active Secure Assessments.

## 15. Separation of Concerns / Anti-Coupling

*   Downstream consumption ≠ ownership.
*   Track signal ≠ Care Case.
*   Path consumption ≠ Passport ownership.
*   Application ≠ Verified Connection ≠ Outcome.
*   Assessment signal ≠ cheating decision.
*   Support Case ≠ Platform Incident.
*   Optional consumer failure ≠ owning-domain failure.
*   Partner access ≠ unrestricted student discovery.

## 18. Later-Unit / Architecture Deferrals

This document explicitly defers the technical *HOW* of integrations. 

MB-08 prohibits Architecture leakage and does NOT define:
*   Postgres use or Modular Monolith mechanics.
*   Domain Service Calls, Application Services, Published Events, or Commands as integration solutions.
*   REST, GraphQL, gRPC, endpoints, or HTTP methods.
*   Payload schemas, event names, topics, or queues.
*   Exact FK vs Event topologies.

## 19. Canonical Invariants / MUST NOT HAPPEN

*   A consumer domain MUST NOT mutate owner truth.
*   Track MUST NOT silently create a Care Case.
*   Application Snapshot MUST NOT be altered by live Passport edits.
*   Partner interactions MUST NOT allow unrestricted student search.
*   Application MUST NOT automatically become a Verified Connection.
*   Secure Assessment MUST NOT fail because Track, Insight, or Partner domains fail.
*   Failure MUST NOT silently transfer domain ownership.
