# ELLIGBLE Agent Context Rules

This document is the SINGLE CANONICAL SOURCE for full New-Agent / New-Chat context reconstruction. `READ_ME_FIRST.md` and `AGENTS.md` explicitly defer to this file instead of maintaining incompatible independent entry orders.

## Required New-Agent Entry Algorithm

### PHASE A — BOOTSTRAP
1. Read: `READ_ME_FIRST.md`
2. Read: `AGENTS.md`
3. Verify actual repository (Git working-state inspection happens BEFORE treating dynamic state files as complete truth):
   - `git rev-parse --show-toplevel`
   - `git branch --show-current`
   - `git rev-parse HEAD`
   - `git status --short`

### PHASE B — CANONICAL BASELINE
Read:
- `docs/master/MASTER_CONTEXT.md`
- `docs/state/CURRENT_STATE.md`
- `docs/state/HANDOFF_PACKET.md`
- `docs/DOCUMENT_MANIFEST.md`
- `docs/00-governance/00.02_DECISION_HIERARCHY.md`
- `docs/00-governance/00.03_CANONICAL_TERMINOLOGY.md`
- active phase index
Then relevant phase/domain predecessors.

### PHASE C — WORKING-STATE RECONSTRUCTION
If `git status --short` is CLEAN: `CURRENT_STATE`, `HANDOFF`, and phase index may describe the synchronized working baseline, subject to normal consistency checks.

If working tree is NOT CLEAN: the agent MUST NOT assume `CURRENT_STATE` alone describes the actual in-progress state.
The agent must:
1. enumerate every modified/untracked project path;
2. inspect each relevant working file;
3. determine: file purpose, status header, version, current phase/unit, whether it is an active draft/correction/review artifact;
4. compare working evidence with `CURRENT_STATE`/`HANDOFF`/phase index;
5. classify state files as: SYNCHRONIZED CURRENT STATE or LAST SYNCHRONIZED BASELINE;
6. reconstruct ACTUAL ACTIVE WORKING STATE;
7. preserve existing work;
8. do not restart an already-active unit merely because state-sync files have not yet been updated.

### PHASE D — CONTEXT GATE
Before editing anything, agent must be able to state:
- REPOSITORY ROOT
- BRANCH
- HEAD
- ORIGIN/MAIN if available
- WORKING TREE STATUS
- LAST LOCKED UNIT
- ACTIVE WORKING UNIT
- ACTIVE STAGE
- ACTIVE FILE(S)
- LOCKED PREDECESSORS
- OPEN/PROVISIONAL constraints relevant to task
- FILES ALLOWED TO CHANGE
- NEXT SAFE ACTION

If these cannot be determined consistently: CONTEXT GATE = BLOCKED. Do NOT proceed by guessing.

## Context Budget Rule

If one execution appears to require several unrelated major domains, stop expanding scope and split the work.

## No Duplicate Truth

Do not copy a full canonical specification into multiple files. Reference the canonical source and summarize only the minimum required context.

## No Silent Inference

If a requirement is `OPEN`, the agent must not choose an implementation and later treat it as canonical.

## Recovery Archive Rule

`docs/00-recovery/archive/ELLIGBLE_RECOVERY_FULL_ARCHIVE.md` is never a default context file.

Use it only when modular/canonical documentation does not contain enough historical evidence.

## Working Tree Safety Rule

A modified/untracked file is evidence of possible in-progress work.

Before modifying, reverting, rejecting, deleting, or replacing it:
- inspect it;
- identify its purpose/status/version;
- compare it with current phase;
- preserve it unless the current authorized task explicitly permits modification.

Especially prohibit destructive cleanup based solely on stale state metadata.
Never use destructive cleanup merely to make Git appear clean. "Clean repository" is NOT more important than preserving authorized in-progress work.

Use exact terminology:
CLEAN
EXPECTED WORKING CHANGE
UNEXPECTED WORKING CHANGE

Do not call a repository CLEAN when `git status --short` is non-empty.

## Evidence-Over-Summary Rule

AGENT SUMMARY = NON-AUTHORITATIVE CLAIM
EXTERNAL REPORT = EVIDENCE INPUT, NOT CANONICAL BY ITSELF
ACTUAL REPOSITORY FILE CONTENT + CANONICAL STATUS/AUTHORITY + GIT/TERMINAL OUTPUT + DIFF/HASH WHEN RELEVANT = VERIFICATION EVIDENCE

If an agent summary says PASS, READY, CLEAN, LOCKED, 0 gaps, all mapped, or all corrected, but evidence disagrees: EVIDENCE WINS.
The stage must not advance merely because the producing agent self-certified PASS. Independent verification is required at relevant gates.

## Chat / Memory Rule

Chat history, Agent memory, Previous conversation summaries, and External handoff summaries are NON-CANONICAL context aids.
They may help locate evidence. They may NOT silently override repository canonical decisions.
If chat says one thing and current canonical repository evidence says another: repository authority wins.
If a report from another chat/agent is introduced: treat it as untrusted evidence input; verify against the current repository before acting.

## State File Semantics During An Active Unit

Normal project lifecycle remains:
READ CONTEXT -> DRAFT -> GAP CHECK -> CORRECTION -> FINAL REVIEW -> LOCK -> SYNC STATE -> GIT VERIFY / COMMIT / PUSH -> NEXT UNIT

Therefore `CURRENT_STATE`, `HANDOFF_PACKET`, `DOCUMENT_MANIFEST`, and phase index may legitimately remain at the LAST SYNCHRONIZED BASELINE while an uncommitted working unit is in progress.
That is NOT itself corruption.

However:
A new agent must detect and reconstruct the newer active working state through Git/filesystem inspection before acting.
Do NOT change the established rule by forcing state-sync edits at every Draft/Gap Check/Correction stage.
