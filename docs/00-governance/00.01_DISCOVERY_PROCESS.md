# 1. Purpose

Dokumen ini menetapkan proses resmi discovery, specification, implementation, verification, handoff, dan continuity untuk pembangunan ELLIGBLE.

Dokumen ini dibuat agar:

1. keputusan produk tidak hanya tersimpan di percakapan;
2. requirement dapat dilacak dan diaudit;
3. AI agent tidak kehilangan konteks;
4. AI agent tidak memperluas scope secara sepihak;
5. fitur besar dipecah menjadi unit kecil;
6. setiap unit dapat diuji secara independen;
7. setiap perubahan dapat di-review dan di-rollback;
8. coding tidak dimulai sebelum requirement cukup jelas;
9. status `DONE` tidak diberikan hanya karena code sudah ditulis;
10. seluruh pembangunan mengikuti Source of Truth yang sama;
11. implementasi awal dapat memanfaatkan InsForge secara penuh;
12. business/domain logic ELLIGBLE tidak terkunci permanen pada satu backend provider;
13. web dan mobile menggunakan business rules yang sama;
14. tenant isolation, security, dan data integrity menjadi requirement sejak awal;
15. pengalaman utama siswa dirancang dengan prinsip mobile-first;
16. seluruh fitur wajib tetap adaptif untuk Android, iOS, tablet, dan PC sekolah sesuai peran dan use case.

# 2. Core Development Principle

ELLIGBLE menggunakan prinsip:

> **Discover small → Decide → Specify → Build small → Verify → Commit → Continue**

Pendekatan berikut tidak diperbolehkan:

> “Bangun seluruh fitur besar sekaligus, lalu diperiksa di akhir.”

Setiap fitur besar harus dipecah menjadi unit sekecil mungkin yang masih menghasilkan satu capability yang dapat diuji.

# 4. Build Unit Principle

`Build Unit` adalah unit implementasi terkecil yang:

- memiliki objective yang jelas;
- memiliki scope terbatas;
- memiliki acceptance criteria;
- dapat diuji;
- dapat di-review;
- dapat di-commit;
- dapat di-rollback tanpa merusak keseluruhan platform;
- memiliki dependency yang diketahui;
- memiliki verification profile yang jelas.

Contoh Build Unit yang baik:

> Guru dapat menambahkan satu siswa yang eligible sebagai peserta ujian dan assignment tetap tersimpan setelah halaman dimuat ulang.

Contoh Build Unit yang terlalu besar:

> Bangun seluruh sistem peserta ujian.

Contoh Build Unit yang terlalu kecil:

> Ubah warna satu tombol.

---

# 5. One Build Unit Per Execution

Default execution policy:

> **ONE BUILD UNIT PER AGENT EXECUTION**

Agent tidak boleh otomatis melanjutkan ke Build Unit berikutnya setelah menyelesaikan unit aktif.

Setelah implementation dan verification selesai, agent harus:

1. menghasilkan implementation report;
2. menunjukkan hasil verification;
3. menunjukkan `git status`;
4. menunjukkan `git diff --stat`;
5. memastikan tidak ada unrelated changes;
6. memperbarui Current State jika scope mengizinkan;
7. berhenti.

Build Unit berikutnya membutuhkan instruction berikutnya.

# 7. Standard Status

## 7.1 Discovery Status

### OPEN
Pertanyaan belum memiliki keputusan.

### PROVISIONAL
Sudah memiliki arah sementara tetapi masih dapat berubah.

### LOCKED
Keputusan dianggap final untuk baseline saat ini.

Perubahan terhadap keputusan `LOCKED` harus masuk `Decision Log`.

### DEFERRED
Keputusan sengaja ditunda.

### FUTURE
Sudah diketahui kebutuhannya tetapi bukan bagian release aktif.

---

## 7.2 Build Status

```text
PLANNED
READY
IN_PROGRESS
IMPLEMENTED
VERIFYING
VERIFIED
COMMITTED
CLOSED
```

### PLANNED
Unit telah teridentifikasi tetapi belum siap dibangun.

### READY
Telah memenuhi Definition of Ready.

### IN_PROGRESS
Sedang dikerjakan.

### IMPLEMENTED
Code telah ditulis tetapi verification belum selesai.

### VERIFYING
Sedang menjalani Quality Gate.

### VERIFIED
Seluruh verification yang diwajibkan berhasil.

### COMMITTED
Perubahan telah memiliki Git checkpoint yang valid.

### CLOSED
Dokumentasi/state sudah sinkron dan pekerjaan dianggap selesai.

# 12. Agent Scope Rules

Agent MUST NOT:

- implement next Build Unit automatically;
- modify unrelated module;
- perform unrelated refactor;
- silently change architecture;
- silently change database schema;
- silently change API contract;
- silently change permission model;
- remove security controls agar test lolos;
- disable tests agar build berhasil;
- expose secrets;
- commit `.env`;
- hardcode tenant-specific behavior;
- assume terminal commands succeeded;
- claim `DONE` without verification;
- bypass provider abstraction hanya untuk mempercepat coding;
- import infrastructure SDK langsung ke domain layer;
- memindahkan business rule ke UI hanya karena implementasinya lebih cepat.

# 13. Stop Conditions

Agent wajib berhenti jika menemukan:

## Architecture Conflict

Implementation membutuhkan perubahan terhadap architecture yang telah `LOCKED`.

## Security Conflict

Task dapat menyebabkan:

- tenant data leakage;
- authorization bypass;
- session vulnerability;
- exposure of student data;
- unsafe secret handling.

## Data Integrity Risk

Perubahan berpotensi:

- menghapus data;
- menduplikasi data kritis;
- kehilangan jawaban ujian;
- merusak submission;
- menghasilkan inconsistent state.

## Scope Expansion

Task membutuhkan perubahan signifikan di module lain yang tidak tercantum pada Build Unit.

## Unresolved Requirement

Tidak tersedia keputusan produk yang cukup aman untuk diimplementasikan.

## Provider Boundary Conflict

Task hanya dapat dilakukan dengan cara yang melanggar provider abstraction yang telah ditetapkan.

Pada kondisi tersebut agent menghasilkan:

```text
BLOCKED
```

beserta alasan teknisnya.

Agent tidak diperbolehkan menebak keputusan produk kritis.

# 14. Backend Architecture Principle

ELLIGBLE menggunakan prinsip:

> **INSFORGE-FIRST, PROVIDER-AGNOSTIC**

Artinya:

- InsForge adalah primary backend implementation pada tahap awal;
- InsForge bukan domain architecture ELLIGBLE;
- business logic ELLIGBLE tidak boleh bergantung langsung pada provider-specific SDK jika dapat dihindari secara wajar;
- external infrastructure harus berada di boundary yang jelas;
- provider dapat diganti, dikombinasikan, atau dipecah di masa depan tanpa rewrite besar pada domain dan UI.

# 23. Database Portability Reality

ELLIGBLE tidak mengasumsikan database dapat diganti dengan satu klik.

PostgreSQL-specific capabilities seperti:

- schema;
- constraints;
- indexes;
- transactions;
- migrations;
- Row Level Security;
- SQL semantics;

dapat tetap menjadi bagian architecture.

Tujuan provider abstraction adalah:

> mengendalikan dependency dan menempatkan provider-specific code pada boundary yang jelas.

Bukan:

> berpura-pura bahwa seluruh backend dapat diganti tanpa migration effort.

# 26. Assessment Persistence Rule

Untuk Assessment:

> **Answer persistence MUST NOT depend on proctor realtime availability.**

Conceptually:

```text
ANSWER PERSISTENCE
≠
PROCTOR REALTIME
```

Jika realtime monitoring gagal:

- jawaban siswa tetap harus tersimpan;
- submit tetap aman;
- autosave tetap berjalan sesuai recovery strategy;
- event monitoring dapat melakukan recovery terpisah.

# 27. Secrets Rule

Secrets dan privileged credentials:

```text
MUST NOT:
- berada di frontend;
- berada di mobile bundle;
- masuk Git;
- masuk dokumentasi;
- masuk screenshot;
- masuk prompt;
- masuk log client.

MUST:
- dikelola melalui trusted environment;
- digunakan hanya pada trusted server/backend/tooling scope;
- mengikuti least-privilege principle.
```

Agent dilarang menyelesaikan error dengan memindahkan privileged credential ke client.

# 28. Multi-Tenant Rule

ELLIGBLE adalah platform multi-tenant.

Tenant utama:

```text
SMA / SMK / MA / sederajat
```

SMA N 1 Mlati adalah pilot/reference tenant.

Tidak boleh ada hardcoded behavior khusus SMA N 1 Mlati pada core platform.

Setiap feature yang menyimpan atau membaca tenant-owned data wajib mempertimbangkan:

- tenant ownership;
- tenant membership;
- authorization;
- tenant isolation;
- cross-tenant negative testing;
- auditability.

Frontend hiding bukan security boundary.

---

# 29. Tenant Isolation Verification

Jika Build Unit menyentuh tenant-owned data, verification minimal harus menguji:

```text
Tenant A user → Tenant A data
ALLOW

Tenant A user → Tenant B data
DENY

Unauthorized role → privileged tenant action
DENY

Anonymous user → private student data
DENY
```

Test harus dilakukan pada trusted backend/database boundary.

# 31. Mobile-First, Multi-Device Rule

ELLIGBLE menggunakan prinsip:

> **MOBILE-FIRST, MULTI-DEVICE — NOT MOBILE-ONLY**

Alasan utama:

- mayoritas siswa mengakses platform melalui smartphone;
- Android diperkirakan menjadi perangkat utama siswa;
- sebagian siswa menggunakan iPhone/iOS;
- sebagian aktivitas sekolah menggunakan tablet;
- laboratorium, ruang ujian, guru, operator, kepala sekolah, dan admin dapat menggunakan PC/laptop sekolah.

Karena itu, desain dan implementasi harus mengutamakan experience pada layar kecil terlebih dahulu, lalu berkembang secara adaptif ke layar yang lebih besar.

Target client architecture:

```text
ELLIGBLE Backend / Services
├── Mobile Client
│   ├── Android — primary student target
│   └── iOS — supported target
├── Tablet Experience
│   ├── Android Tablet
│   └── iPad
└── Web/Desktop Client
    ├── Student
    ├── Teacher
    ├── Proctor
    ├── School Admin
    ├── Principal
    ├── Counselor
    ├── Parent
    ├── Partner
    └── Platform Owner
```

## 31.1 Mobile-First UX

Untuk feature yang digunakan siswa:

1. desain dimulai dari viewport smartphone;
2. primary action harus mudah dijangkau;
3. navigasi tidak boleh bergantung pada hover;
4. touch target harus memadai;
5. form tidak boleh sulit digunakan dengan virtual keyboard;
6. tabel besar harus memiliki mobile alternative;
7. modal/dialog harus memiliki mobile behavior yang aman;
8. loading state dan reconnect state harus jelas;
9. bandwidth dan device performance harus dipertimbangkan;
10. feature tidak boleh hanya "dikecilkan" dari desktop layout.

## 31.2 Responsive / Adaptive Behavior

ELLIGBLE tidak menggunakan asumsi bahwa satu layout dapat sekadar diperkecil.

Setiap feature harus menentukan behavior minimal untuk:

```text
PHONE
TABLET
DESKTOP
```

Jika diperlukan, feature dapat mempunyai presentation berbeda dengan business rules yang tetap sama.

Contoh:

```text

→ card/list compact
→ filter sheet
→ bottom action

→ wider list
→ split information panel

→ data table
→ bulk actions

```

## 31.5 Mobile App Readiness

Walaupun implementasi awal dapat dimulai dari web pada beberapa module, architecture harus menghindari web-only coupling.

Business logic penting harus berada di:

```text

```

dan bukan tertanam eksklusif di:

```text

browser-only hook
DOM event
local browser state
```

jika logic tersebut juga dibutuhkan aplikasi mobile.

## 31.6 Offline and Weak Connection

Mobile-first berarti koneksi tidak stabil dianggap kondisi normal yang harus dipikirkan.

Setiap relevant Build Unit wajib menentukan:

```text
Online behavior
Weak connection behavior
Offline behavior
Retry strategy
Conflict strategy
Sync strategy
User feedback
```

Khusus Assessment:

- answer persistence menjadi prioritas tertinggi;
- reconnect tidak boleh membuat jawaban hilang;
- duplicate submission harus dicegah;
- local queue/offline strategy harus dirancang jika dibutuhkan;
- monitoring realtime boleh mengalami degradasi tanpa menghentikan answer persistence.


Tidak semua Build Unit wajib dites pada semua device setiap execution.

Tetapi setiap Module Gate dan Release Gate harus memiliki device coverage yang ditentukan secara eksplisit.

## 31.10 Mobile Performance

Mobile target harus mempertimbangkan perangkat dengan kemampuan menengah/rendah.

Discovery dan implementation harus memperhatikan:

- JavaScript bundle size;
- image/media size;
- lazy loading;
- unnecessary realtime subscription;
- memory usage;
- battery usage;
- network requests;
- background activity;
- rendering complexity.

## 31.11 Touch and Accessibility

UI mobile harus:

- memiliki touch target yang cukup;
- mendukung orientation yang diputuskan;
- tidak mewajibkan gesture tersembunyi untuk action kritis;
- memiliki visual feedback;
- mempertimbangkan font scaling;
- mempertimbangkan contrast;
- mempertimbangkan screen reader pada feature yang relevan.

## 31.12 Orientation Strategy

Default:

```text
General student app
→ Portrait-first

Content / dashboard tertentu
→ Portrait + Landscape bila bermanfaat

Assessment
→ ditentukan per exam mode dan platform capability

Proctor dashboard
→ Landscape/Desktop-first
```

Orientation tidak boleh dikunci secara global tanpa kebutuhan.

## 31.13 Platform-Specific Code Boundary

Jika suatu capability membutuhkan implementation khusus Android/iOS/web:

```text
Shared Domain
↓
Shared Application Contract
↓
Platform Adapter
├── Android
├── iOS
└── Web
```

Platform-specific behavior tidak boleh menyebabkan duplikasi business rule tanpa alasan.

## 31.14 Mobile-First Verification Requirement

Build Unit dengan user-facing UI harus menyatakan minimal:

```text
Primary viewport
Secondary viewport
Touch behavior
Responsive/adaptive behavior
Keyboard behavior
Loading state
Error state
Weak-network state
Accessibility considerations
```

Untuk Student-facing feature, default Primary Viewport adalah smartphone.

## 31.15 Desktop Remains First-Class

Mobile-first tidak berarti desktop menjadi versi sekunder yang buruk.

Desktop adalah first-class experience untuk use case seperti:

- question authoring;
- exam builder;
- bulk participant management;
- proctor monitoring;
- school administration;
- analytics;
- reporting;
- platform administration;
- support operations.

Desain desktop boleh menggunakan density dan multi-column layout yang tidak cocok untuk smartphone.

# 35. Terminal Verification Principle

Code yang terlihat benar belum dianggap selesai.

Setiap Build Unit wajib menjalankan verification sesuai Verification Profile.

Baseline:

```bash
git status
git diff --stat
git diff
```

Untuk application code, sesuai stack:

```bash
npm run typecheck
npm run lint
npm run test
npm run build
```

Untuk E2E:

```bash
npx playwright test <target>
```

Command final mengikuti package manager dan stack yang dikunci kemudian.

# 41. Git Principle

Setiap perubahan harus dapat ditelusuri.

Sebelum task ditutup:

```bash

git diff --stat
git diff
```

- hanya intended files berubah;
- tidak ada secret;
- tidak ada unrelated refactor;
- tidak ada dependency change tanpa alasan;

- tidak ada generated file yang tidak diperlukan;
- test output sesuai expectation.
