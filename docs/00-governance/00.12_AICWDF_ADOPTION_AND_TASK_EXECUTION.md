# AICWDF v4.3 Adoption and Task Execution Model

## 1. Decision

The Owner adopts AICWDF v4.3 as the planning and operating framework of ELLIGBLE, adapted to this active repository: preserve valid work, fill real gaps, reduce executor ambiguity and keep traceability. The repository is not reset or restructured to look like the framework template.

- The Git repository stays the durable Source of Truth. Chat, project memory, summaries and agent reports are context only; a decision made in chat becomes durable only when it is written into the repository.
- Authority resolution stays `00.02_DECISION_HIERARCHY.md`. AICWDF never overrides a LOCKED or FROZEN repository decision; its §3 hierarchy applies only where 00.02 is silent.
- The operative rules are restated in this document, so an agent does not need the framework file to execute. Reference copy of the framework: `docs/00-governance/reference/AICWDF_v4.3_EN.md`.

## 4. Execution flow and roles

1. A planning or review agent (Claude Project chat or equivalent) reconstructs the current state from the repository.
2. It identifies one bounded Task with a contract (§5).
3. The Owner authorizes that Task by ID.
4. The executor (Claude Code Desktop on `C:\Projects\ELLIGBLE`, unless the Owner approves another path) implements only that scope.
5. The executor runs the required tests and records the evidence.
6. The executor updates the Task record (status history, evidence), TASK_PLAN.md once it exists, and the living plan's evidence and continuity checkpoint in the same change.
7. A HIGH-risk Task is reviewed independently against its evidence; the review result is recorded in the Task record before the Task becomes DONE.
8. Only then does the next Task start.

The executor never merges into `main`; the Owner merges. Inside a Task, the 00.10 §3 stop conditions still apply: stop, record, and ask one concise question with a recommended default.

A new agent with no chat history reconstructs the state from AGENTS.md, READ_ME_FIRST.md, `docs/production/EXECUTION_CONTEXT.md`, TASK_PLAN.md, the Task records in `docs/production/tasks/` and living plan §14, after the Git baseline check of 00.04.

## 5. Task rules

- **Baseline:** published when P1 to P10 are sufficient. It shows Baseline Total, Current Total, DONE, READY, IN_PROGRESS, BLOCKED, VERIFYING, TODO, SUPERSEDED and Progress % (DONE ÷ Current Total).
- **Baseline scope:** the work from the adoption point to the CBT Release Gate (00.11 §9). Capabilities delivered before adoption are listed as "pre-baseline delivered capabilities (reused)" with commit and CI evidence; they are not counted as baseline DONE.
- **Pre-baseline Tasks:** a Task authorized before the P11 baseline is approved is marked PRE-P11 / PRE-BASELINE and NOT COUNTED IN THE P11 BASELINE; every other rule of this section applies to it. GOV-REALIGN-001 is the first. TASK_PLAN.md, once it exists, lists such Tasks only as pre-baseline history.
- **IDs:** stable. The existing workstream scheme continues (for example UI-SYSTEM-002, ASSESS-PROCTOR-003) and new Tasks use it. A split Task becomes SUPERSEDED with its replacements named; every plan change is recorded with the AICWDF §22.6 block.
- **READY gate (AICWDF §22.8):** dependencies DONE; requirement clear; scope bounded; acceptance criteria and tests defined; database, route and interaction, UI and localization, and cost impact known; tools available; no blocking ambiguity.
- **Contract and record:** one file per Task in `docs/production/tasks/`, named after the Task ID (for example `GOV-REALIGN-001.md`), holds the contract (the AICWDF §23 fields, N/A where not applicable) and the Task record: status and status history, Owner approval and authorization, base and branch, completion evidence and the independent review. A commit never records its own SHA. The content commits of a Task, with their attribution checks and the full CI result of the latest one, and the independent review are recorded by one evidence commit on the Task branch that changes only the Task record. The evidence commit is verified locally and deterministically; it is not the subject of a further evidence commit, and its own CI run is not a DONE prerequisite. The landing commit on `main` is recorded by the next Task.
- **Size:** one coherent outcome that can be verified end to end (AICWDF §22.10).
- **Risk class HIGH** for: answer integrity, timer, submission, session and device control, authentication, authorization, tenant isolation, identity verification and recovery, schema evolution, scoring and results, concurrency, security, production infrastructure, governance authority changes.
- **DONE:** the required tests pass and the evidence (commands, results, commit, CI run) is recorded in the Task record; a HIGH Task also needs an independent review PASS recorded there. VERIFYING is not DONE. The checkbox in TASK_PLAN.md and the counters change only then, in the same change.

## 6. Verification layers

1. **Task verification:** targeted tests plus static and build gates; the 00.10 §4 standard for any Task that touches a critical journey.
2. **Critical-journey regression:** after a group of related Tasks and before staging.
3. **Full release regression:** before production: all critical journeys and roles, mobile and desktop, security, load evidence, real-device evidence, the PB-07 artifact.

## 7. Git and branch protocol

- Commits use only the Owner's configured author and committer identity. Before the first commit of a session, the executor checks `git config user.name` and `git config user.email`; if they are not the Owner's identity, it stops and asks, and never sets an identity itself.
- No AI, model or tool attribution anywhere: no Co-Authored-By, Generated-By, Assisted-By or session-link trailers, and no Claude, Anthropic, Fable, Opus, ChatGPT or OpenAI attribution in commits, trailers, pull request metadata or contributor metadata. Commit messages describe the software change only.
- After every commit, the executor inspects `git log -1 --format=fuller` and the raw message (`git log -1 --format=%B`). On any attribution it stops and reports. History is not rewritten without an explicit Owner instruction.
- Historical attribution is not rewritten: `Agent <agent@example.com>` on `main` up to `3a69883`; `Claude <noreply@anthropic.com>` on the `claude/laughing-mendel-p2l9gh` branch.
- One branch per Task from the current `main`, named `task/<task-id>-<slug>`; one pull request per Task; CI must pass. The Owner reviews and squash-merges, removes any `Co-authored-by` trailer GitHub proposes in the squash message, then checks the raw commit on `main`.
- No force push. No rewriting of published history. A normal push only when the active Task authorizes it.
- Never a destructive cleanup of unknown work (00.04 working-tree preservation).

## 8. Toolchain policy

Tools are activated per Task, on demand; repository evidence beats every tool (AICWDF §5 to §7, §6A).

- Current documentation (Context7 or the official documentation) for version-sensitive library and runtime facts.
- Graphify for impact analysis of HIGH Tasks, as derived navigation only (authority guard in `.agents/rules/graphify.md`).
- Playwright for critical journeys; the five-project CI matrix stays.
- shadcn/ui and the shared ELLIGBLE primitives before any new primitive (DEC-043, living plan §10.1).
- DesainPakeAI only as a verified reference, after confirming project `b5a22aa4-7b38-49d2-9448-443eab6e8075` and its revision.
- Load testing with an open-source tool chosen in P6; no paid service without Owner approval.
- The verified state of each tool is recorded in `docs/production/TOOLCHAIN.md`.
