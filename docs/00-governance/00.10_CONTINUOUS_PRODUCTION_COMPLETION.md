## 3. Execution model

1. Reconstruct state from Git and the repository (00.04), then read the living plan.
2. Pick the highest-value dependency-valid item on the critical path (P0 before P1, baseline before OPTIONAL/FUTURE, Secure Assessment first).
3. Implement it as a coherent vertical result (database, runtime, HTTP, UI, tests) when the product result needs all layers.
4. Verify it (§4), fix defects, commit at coherent checkpoints, push through the normal branch / pull request workflow.
5. Update the living plan in the same change: capability state, gaps, evidence, next work. Do not write separate lifecycle reports.
6. Continue with the next clear critical-path item.

Stop only for **OWNER DECISION REQUIRED**: a genuinely conflicting valid business policy, a legal/policy decision (for example PB01, PB02, PB03, PB05, PB10), a new paid external provider or new platform-wide vendor, missing external access or credentials, an irreversible production action, or materially different product outcomes only the Owner can choose. Ask one concise question with a recommended default and its impact.

## 4. Verification standard

Use the strongest appropriate evidence for the change: typecheck, unit tests, real PostgreSQL integration tests, HTTP contract tests, authorization/tenant-isolation negative tests, browser end-to-end tests, rendered responsive checks, production build and production startup/preflight. A change that touches a critical journey is not done until that journey passes through the real stack. Passing unit tests alone never proves a working product.

"Production-ready" requires, at minimum: no known P0 defect, no known P1 baseline blocker, no broken baseline route, no production mock or fake dependency, no known tenant-isolation violation or authorization bypass, no known critical data-loss path, critical browser E2E pass, real PostgreSQL pass, production build and startup/preflight pass, migration verification pass, and Production Blockers truthfully tracked.

## 5. Evidence

Record concise evidence in the living plan (command, result, commit). Git commits and pull requests are the audit trail. Do not create per-change evidence files unless a defect or forensic investigation needs preserved output.
