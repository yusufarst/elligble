# ELLIGBLE Build Execution Rules

## One Build Unit Per Execution

```text
ONE BUILD UNIT
=
ONE CONTROLLED AGENT EXECUTION
```

Do not bundle unrelated domains into one coding run.

## No Silent Scope Expansion

A Build Unit may not “also”:

- install AI SDKs;
- redesign unrelated navigation;
- change authentication architecture;
- add new vendors;
- change pricing;
- create unrelated modules;
- resurrect `FUTURE`, `DROP`, or `LEGACY` features.

If a dependency is discovered, report and classify it instead of expanding implementation silently.

## Terminal Verification Is Mandatory

A future Build Unit cannot be `DONE` merely because the agent says it is complete.

Verify relevant items such as:

```text
typecheck
lint
unit tests
integration tests
build
migration status
security checks
critical-flow checks
git diff
git status
```

## Documentation Is Part of Done

Update only the canonical documentation affected by the Build Unit, including `CURRENT_STATE.md` and Decision Log/ADR when required.

## Database Rules

- Database changes use versioned Git migrations.
- Do not edit production schema manually as source of truth.
- Shared PostgreSQL does not mean shared domain ownership.
- Cross-domain writes follow explicit contracts.

## Legacy Rules

Never wholesale-copy legacy `src/`, migrations, RLS, RPC, authentication, or database folders.

Legacy code requires file-level audit before `PORT`.

## Secrets

Never put passwords, admin keys, tokens, secrets, or production credentials into Git, source code, screenshots, documentation, prompts, or unsafe logs.

## Assessment Priority

During active exams, answer persistence, timer authority, submission, and essential security outrank analytics, search, messaging, partner, billing, and other noncritical capabilities.
