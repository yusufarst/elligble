# Product Milestone-Driven Build Control

## 1. Core Principle: Product Over Build Units

**THE PRODUCT IS THE GOAL. BUILD UNITS ARE CONTROLLED EXECUTION TOOLS.**

ELLIGBLE exists to deliver a complete, robust, secure, multi-tenant education superapp. Development must never optimize for Build Unit quantity, arbitrary numbering increments, or endless horizontal layer decomposition at the expense of working vertical product capabilities.

Every Build Unit must deliver verifiable, durable progress toward an active product milestone and ultimately full product completion. Once a Build Unit is sufficiently specified:
- **IMPLEMENT**
- **TEST**
- **VERIFY**
- **CLOSE**

Successor selection must reduce the remaining gap to the active product milestone and the formal Baseline Completion Gate. Creating milestone-irrelevant horizontal micro-BUs is strictly prohibited and requires explicit Controller justification.

## 2. The Two Strategic Programs

ELLIGBLE shall be built across two major completion programs:

```text
┌────────────────────────────────────────────────────────────────────────┐
│ PROGRAM 1: CANONICAL BASELINE COMPLETION                               │
│ Scope: IN — CORE and IN — MANDATORY BASELINE                          │
│ Priority: Highest and exclusive implementation priority               │
└────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
                     [ BASELINE COMPLETION GATE ]
                     (Passes only when 100% baseline
                      is usable, integrated & verified)
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ PROGRAM 2: POST-BASELINE EXPANSION                                     │
│ Scope: OPTIONAL capabilities, followed by FUTURE capabilities         │
│ Priority: Begun ONLY after Program 1 passes Baseline Completion Gate  │
└────────────────────────────────────────────────────────────────────────┘
```

### Program 1 — Canonical Baseline Completion
Program 1 comprises all approved `IN — CORE` and `IN — MANDATORY BASELINE` scope across canonical domains, including all functional, architectural, cross-cutting, and user-facing requirements necessary to make those capabilities usable, integrated, and production-ready.

Program 1 is the sole and exclusive implementation focus of the project until the Baseline Completion Gate is passed.

### Program 2 — Post-Baseline Expansion
Only after Program 1 has formally satisfied and passed the Baseline Completion Gate may development proceed into Program 2:
1. **OPTIONAL** capabilities
2. **FUTURE** capabilities

Program 2 work must never interrupt, divert, or delay Program 1 baseline completion.

## 3. Non-Negotiable Baseline-First Rule

**BASELINE FIRST. OPTIONAL/FUTURE LATER.**

While any required `IN — CORE` or `IN — MANDATORY BASELINE` product capability remains incomplete, unusable, materially unintegrated, or blocked from production readiness:
- `OPTIONAL` and `FUTURE` implementations are **NOT ELIGIBLE** for normal successor selection.
- No Build Unit may target `OPTIONAL` or `FUTURE` scope merely because:
  - it is easier to implement;
  - it is visually attractive;
  - it is technically interesting;
  - it has fewer dependencies;
  - it can be finished quickly.

The active objective remains 100% completion and verification of canonical baseline product scope.

## 4. The Baseline Completion Gate

The **BASELINE COMPLETION GATE** is a formal strategic milestone that terminates Program 1 and authorizes Program 2.

The Baseline Completion Gate may **PASS** only when all approved baseline and core product scope across all canonical domains is:
1. **IMPLEMENTED:** Fully authored without placeholder stubs.
2. **INTEGRATED:** Connected end-to-end across database, runtime, API, and UI layers.
3. **ROLE-USABLE:** Capable of fulfilling actual user journeys for students, teachers, proctors, and school administrators.
4. **USER-FACING WHERE REQUIRED:** Surfaced through responsive, secure, localized browser UI where user interaction is specified.
5. **VERIFIED:** Validated with automated unit, regression, and real PostgreSQL verification.
6. **CROSS-DOMAIN COHERENT:** Compliant with multi-tenant data isolation and logical domain boundaries.
7. **SECURE:** Enforcing authentication, authorization, split-screen/environment guards, and privacy defaults.
8. **RELIABLE:** Proven crash-resilient, recoverable, idempotent, and failure-contained.
9. **PRODUCTION-READY:** Backed by versioned migrations, seed fixtures, operational monitoring, and zero blocking defects.
10. **PRODUCTION BLOCKERS RESOLVED:** All Production Blockers applicable to baseline launch scope are formally closed.

### Negative Invariants
- **Backend-only completion DOES NOT satisfy this gate.**
- **Database-only completion DOES NOT satisfy this gate.**
- **UI-only completion DOES NOT satisfy this gate.**
- **A high Build Unit count DOES NOT satisfy this gate.**

## 5. Canonical Scope & Domain Alignment

Scope classifications adhere strictly to `docs/02-master-blueprint/02.10_BASELINE_FUTURE_AND_EXCLUSIONS.md` (MB-10). Canonical domains encompassed by Program 1 include:
- **Identity / Tenant / Access:** Multi-tenant boundaries, RBAC, authentication, session security.
- **Academic Core:** Academic years, periods, subjects, grade levels, classes/groups, enrollments, teaching assignments.
- **Secure Assessment:** Flagship domain. Authoring, delivery, timing, proctoring, room operations, autosave, anti-cheating, submission, scoring.
- **Track:** Longitudinal academic development and progress tracking. Applicable Track examples may include Academic Progress, Early Warning, Targets / Follow-Up, and Portfolio Workbench. Track != Care. Track does NOT own Official School Grade truth. General school attendance is OUT OF CURRENT BASELINE. General school timetable is OUT OF CURRENT BASELINE.
- **Care:** Pastoral care, student support, counseling boundaries, role-restricted notes.
- **Passport:** Verified student academic profile, verified accomplishments, provenance records.
- **Path:** Career & academic progression planning, target mapping.
- **Opportunity:** Verified opportunities, listings, matching rules.
- **Application:** Submission of applications, tracking, review flows.
- **Verified Connection:** School-to-partner, student-to-opportunity verified linkages.
- **Outcome:** Verified graduation, placement, progression outcomes.
- **Alumni / Impact:** Institutional outcomes, school impact tracking.
- **Parent / Guardian:** Parent access portal, student progress monitoring, consent management.
- **Partner:** Institutional partner access, scoped role permissions.
- **Shared Platform Core & Cross-Cutting:** Notifications, Bantuan & Feedback, audit logging, system health, rate-limiting, error containment.

Existing canonical classifications must not be silently altered or diluted.

## 6. Treatment of OPTIONAL and FUTURE Scope

Existing canonical classifications are preserved:
- **OPTIONAL:** DEFERRED UNTIL BASELINE COMPLETION GATE PASS.
- **FUTURE:** DEFERRED UNTIL BASELINE COMPLETION GATE PASS.

Examples include:
- Learn OPTIONAL capabilities (e.g., interactive LMS workflows outside core tracking).
- FUTURE capabilities (e.g., automated camera proctoring, AI-assisted authoring, advanced analytics).

These capabilities remain in their existing status. This governance document establishes strict sequencing: baseline completion first, post-baseline expansion second. It does not promote OPTIONAL or FUTURE scope into baseline, nor does it authorize early implementation.

## 7. Post-Baseline Expansion Program

Passing the Baseline Completion Gate does not end the ELLIGBLE project. Upon gate passage, the project immediately transitions into **Program 2: Post-Baseline Expansion**.

Default priority within Program 2:
1. `OPTIONAL` capabilities (in order of canonical value and dependency readiness).
2. `FUTURE` capabilities (subject to explicit Owner approval and non-blocking constraints).

All Program 2 work remains subject to canonical dependency rules, multi-tenant security, architecture constraints, and explicit Owner decisions where required.


## 9. Reuse of Completed Build Units

**BU-001 THROUGH BU-077 ARE PRODUCT CONSTRUCTION ASSETS.**

The extensive foundation established in BU-001 through BU-077:
- Identity and tenant isolation primitives;
- Core state schema, check constraints, and versioned migrations (0001–0034);
- Authoritative timer, session lock, autosave, and submission convergence;
- Academic Core foundations (academic years, subjects, offerings, enrollments);
- Exam lifecycle state machines, question snapshot freezing, readiness composition preflights;
- Room operations, proctor assignment authorization, and conditional room/proctor preflights;

must be **reused and composed** directly by vertical product work.

Agents and Controllers are strictly forbidden from reimplementing or duplicating existing verified capabilities. New Build Units must import, invoke, or compose existing verified runtime modules and database structures unless material defect evidence, canonical supersession, or authorized integration adaptation requires a modification.

## 10. Preserved Execution Guardrails

This milestone-driven build control operates strictly within locked governance rules:
- **One Build Unit Per Execution:** Exactly one bounded Build Unit per implementation execution. No scope creep or bundled units.
- **Fast-Track Lifecycle Preserved:** Stage 1 (Selection/Freeze) → Stage 2 (Execution) → Stage 3 (Audit) → Stage 4 (Lifecycle Close) → Stage 5 (Verification Sync). Combined administrative cadence; material engineering and verification gates are never skipped.
- **Terminal Verification Mandatory:** Real PostgreSQL, typecheck, unit tests, regression suites, zero-mutation, and leak checks remain non-negotiable before DONE.
- **Git Discipline:** Controlled per-file staging, diff checking, and remote synchronization required.
- **Frontend Entry Gate:** Production frontend implementation MUST NOT START until FRONTEND ENTRY GATE = PASS.
