# Standing Execution Delegation for CBT-R1 Tasks

## 1. Decision

The Owner delegates to the executor a standing authority for the **mechanical execution** of the approved P11 baseline Tasks of CBT-R1:

- identifying and continuing to the next eligible Task;
- the formal READY transition;
- branch, commit, normal push, pull request and CI verification;
- commissioning the Task's independent review;
- evidence recording and delegated acceptance;
- squash merge and post-merge verification;
- tracker updates.

This delegation removes Owner interruptions for routine steps. It waives no gate. Every verification, review, privacy, security, legal, release and architecture rule stays in force, and §7 keeps with the Owner, or with the named external authority, every decision that needs one.

It commits only with the Owner's configured Git identity and uses the Owner's authenticated GitHub CLI account for pushes, pull requests and merges.

## 4. Eligibility and Task flow

1. **Eligible Task.** A baseline Task is eligible when all of the following hold:
   - all its internal dependencies are DONE and landed on `main` with passing post-merge CI;
   - for every external gate TASK_PLAN §8 names for it, the recorded approval of **every responsible authority §8 names for that gate** exists, with the Owner's own approval wherever §8 names the Owner;
   - it depends on no OPEN policy input or unapproved architecture decision;
   - it is not a prepare-only Task under §7.

   A reviewer the executor commissions under §5.5 is never a §8 responsible authority; a §8 reviewer authority is one the Owner designates for that gate. This delegation is not itself the Owner authorization of any reviewer, signatory, technical decision, contract or ADR that TASK_PLAN §4 or §8 requires the Owner to authorize.
2. **Selection.**
   - Pick the highest-priority eligible Task in TASK_PLAN order (P0 before P1, then row order).
   - Exactly one Task is IN_PROGRESS or VERIFYING at any time.
   - The next Task starts only after the previous one is DONE, merged and its post-merge `main` CI has passed.
3. **Contract and READY.**
   - The executor finalizes the Task contract within approved decisions.
   - A HIGH-risk Task requires an independent contract review PASS before READY.
   - At READY the executor freezes and records the exact path allowlist, any migration path (checked unused on current `main`) and the CI-first verification order.
   - The allowlist may never include §7-reserved rule text or decide a §7 item.
   - Expected outcomes are only those already approved in the Task's TASK_PLAN card, its §8 gates and recorded Owner decisions. An expected outcome not so approved is an Owner decision (§7); an independent contract review PASS never approves one.
   - **Task-flow paths:** the Task record, TASK_PLAN, the living plan and the document manifest. They are not part of the allowlist.
     - The Task record holds the Task's contract as finalized and frozen at READY (00.12 §5), its status history, evidence and review records.
     - TASK_PLAN (status rows, checklist, counters, card status, READY-frozen footprint summary and evidence text, checkpoint lines, §11 entries), the living plan and the manifest take status, counter, evidence and checkpoint updates only.
     - No Task-flow change alters §7-reserved rule text.
4. **Execution.**
   - Branch `task/<task-id>-<slug>` from current `main`.
   - Edit only the frozen allowlist and the Task-flow paths.
   - Run targeted local verification within the workstation limits.
   - Verify the Owner identity once per session before committing; after every commit, inspect `git log -1 --format=fuller` and the raw message.
   - Normal push and one PR.
   - Automatic exact-SHA CI with every job SUCCESS on attempt 1, or on an attempt the Owner authorized by name under the TOOLCHAIN re-run rule (§5.3).
   - Rendered evidence for material UI.
   - For a HIGH-risk Task, independent implementation review on the final content SHA.
   - One evidence commit changing only the Task record.
5. **Continuation.**
   - After landing (§6), the next Task's first change records the landing commit and its post-merge CI. The executor then selects the next eligible Task.
   - If no Task is eligible, the executor presents one consolidated Owner decision package in chat, with a recommended default for each blocking input, and stops. The package and the landing record stay as an uncommitted local change to the living plan and TASK_PLAN until the Owner authorizes their publication, or until the next eligible Task's first change includes them.

## 5. Bounds on executor judgment

1. **Engineering detail.**
   - Routine technical detail inside the approved contract is resolved by the executor and recorded in the Task record.
   - It never decides policy, an OPEN input, an architecture decision (§7) or an expected outcome that the contract leaves unapproved.
2. **Allowlist.**
   - Frozen at READY.
   - A path-only addition is permitted only if all of the following hold: it is required to implement the unchanged frozen contract; it adds no route, table, column, dependency, permission, data field, UI surface, acceptance change or §7-reserved rule text; the same independent reviewer confirms its necessity before the edit; and it is recorded.
   - Any other widening goes to the Owner.
3. **CI.**
   - No re-run of any kind. TOOLCHAIN.md's rule stands: a re-run needs a contract rule and the Owner's authorization naming the run.
   - A `workflow_dispatch` run, an empty commit, or a new SHA without a correction counts as a re-run.
   - A failure is diagnosed. A code or test defect is corrected within §5.2 as a new SHA with full CI.
   - An infrastructure failure is escalated (§8).
4. **Delegated acceptance.** The executor may record "Delegated Acceptance (DEC-048)" only when all of the following hold:
   - every acceptance gate of the contract has PASSED with recorded evidence;
   - the independent review has PASSED on the final content SHA;
   - for material UI, the independent reviewer has inspected the actual rendered evidence.

   The Owner may reopen any Task at any time.
5. **Independent review.**
   - The reviewer is separate from the executing context: a fresh-context, read-only reviewer agent given the artifacts and the source but not the executor's conclusions, or a reviewer the Owner names. The fresh-context agent is of the same model family, so its independence is contextual, not organizational.
   - The Task record keeps, for each round: the reviewed SHA, the verdict, and each material finding with its evidence (00.04 evidence over summary).
   - The executor verifies the reviewer's evidence before correcting and never overrides a STOP.
   - A STOP is closed only by a correction re-reviewed by the same reviewer, or by an Owner decision. Commissioning another reviewer to replace a STOP is forbidden.
   - The Owner may require a named external reviewer for any Task.
6. **Bounded correction.** Escalate when a finding cannot be corrected within the frozen contract, or when the same gate or review finding fails three times.

## 6. Delegated squash merge

The executor may squash-merge a delegated Task PR only when all of the following hold:

- The Task is DONE under 00.12 §5.
- The PR head is either its evidence commit, or a normal merge commit of current `main` on top of it (no force push).
- The evidence commit changes only the Task record relative to the CI-verified content SHA.
- After any such update merge, automatic CI ran again on the new head. If the update resolved a conflict or changed a file in the Task's allowlist, the same independent reviewer reviewed that change.
- Automatic CI on the PR head SHA has completed with every job SUCCESS on attempt 1, or on an attempt the Owner authorized by name.
- The PR is mergeable into current `main` without conflict.
- The cumulative PR diff stays inside the frozen allowlist plus the Task-flow paths. The TASK_PLAN, living-plan and manifest changes are status, counter, evidence and checkpoint updates only, and no Task-flow change alters §7-reserved rule text.
- No commit, PR title or body contains AI, model or tool attribution.

The merge uses `gh pr merge --squash` with an explicit subject and body, so no `Co-authored-by` or other trailer is added. Afterwards the executor verifies that:

- the new `main` commit has the Owner author, the expected raw message and no attribution;
- its tree equals the PR head tree;
- the automatic post-merge `main` CI has every job SUCCESS.

A post-merge `main` CI failure stops the delegation chain. There is no automatic revert; the executor escalates.

## 8. Stop and escalate

Stop at a safe point and ask one concise question with a recommended default (00.10 §3) when:

- a §7 item is reached;
- a review STOP cannot be corrected within the frozen contract;
- the §5.6 bound is reached;
- a CI infrastructure failure occurs;
- post-merge `main` CI fails;
- canonical decisions conflict;
- unknown working-tree changes or a Git identity mismatch are found;
- attribution is detected after a commit;
- a security incident or suspected exposure of personal data occurs;
- a required tool or credential is missing.

## 10. Residual risks

- `main` has no GitHub branch protection (GOV-EXEC-001 §7 records the command and output). The merge gates are enforced by executor discipline and recorded evidence. Enabling protection is an Owner-reserved settings change.
- Reviewer independence is contextual, not organizational (§5.5).
- A delegated merge widens the impact of an executor error. The mitigations are exact-SHA CI, independent review, the allowlist diff check, the post-merge CI check, immediate revocation and Owner reopening.
