## 6. Proposed preview, commit, validation and lock protocol

### 6.1 Transport, validation and disclosure

Use P3 F01 names: POST /api/v1/identity/roster/preview and POST /api/v1/identity/roster/confirm. No unapproved general roster GET/search/export. Keep existing auth/Origin/CSRF/security-header conventions. Me/context adds only server-derived schoolOperator capability; visibility never replaces authorization.

Proposed versioned UTF-8 CSV header: source_student_key,full_name,nis,nisn,date_of_birth,academic_group_id. JSON envelope supplies academicYearId, academicPeriodId and CSV; these are untrusted locators and must all be coherent within authenticated tenant. Server resolves group labels for response; no client-supplied name-to-group guessing. Full name 1–200 characters, source key/NIS/NISN 1–64 characters, no NUL/control characters; NIS/NISN retained as strings (leading zeros preserved), not numeric coercion or purported national-registry validation. Calendar date is strict existing isIsoDate. Names never become equality/identity keys. Duplicate source keys, duplicate NIS or NISN/date-of-birth conflicts within file/current tenant produce specific row codes without another Student's private record. No global sensitive-field uniqueness claim or cross-tenant match enumeration.

Reuse existing CSV parser without changing it unless a demonstrated defect requires separately approved scope. Handle BOM, quoting/commas/newlines, malformed widths/header/empty rows deterministically; forbid formulas being executed/rendered as HTML. No new spreadsheet/parser dependency. Proposed route-local bounds: total JSON request <=1 MiB, <=1,000 rows/file; neither changes global JSON_BODY_LIMIT_BYTES (64 KiB) nor certifies P6 capacity. Reject oversize before writes; verify escaped JSON byte limit as well as CSV count. These bounds are proposed implementation limits, not claims about school cohort size.

Preview is read-only: authenticate, verify active Operator assignment/current tenant, then one consistent snapshot of roster revision and referenced academic state; parse/classify INSERT/UNCHANGED/CORRECTION/INVALID/REVIEW_REQUIRED. Return all per-row codes and minimal fields allowed in D2 plus protocol/input/state digests. No Account/Person/membership/roster/audit receipt write, credential or claim side effect. Do not persist uploaded raw CSV or a sensitive preview cache. Client must retain the exact file bytes/digests in memory only until confirm; tenant change/navigation/logout clears it. No browser localStorage/sessionStorage of roster data, public URLs, logs or screenshots with real data.

Confirm resubmits the same bounded payload, preview digests, UUID request key, reason and confirmed:true. Normalize reason using existing 1–200-character contract. Actor/tenant/timestamps/receipt/binding fields cannot be supplied by client. Recompute validation/preview against current locked state, never trust prior preview as authority. Any stale revision/digest/group/assignment yields bounded conflict, no business/audit-success mutation; UI returns to preview, never silently retries a write. UI only announces success after commit acknowledgement. Repeating a committed request returns its minimal receipt after current authorization; altered payload/reason/preview under same key conflicts. Previously revoked Operator cannot replay or read receipt.

### 6.2 Transaction and concurrency contract

Proposed READ COMMITTED coordinator lock order, fixed before Build and reviewed against every writer:

1. Lock request-key namespace (tenant+authenticated actor+operation+UUID), then tenant roster mutation advisory namespace. No input-dependent raw PII lock labels in logs.
2. Authenticate/resolve current membership with existing Identity session/account mutation guards; then lock current Operator assignment using Tenant Access. Compare actor/tenant again and recheck post-wait session/assignment validity; assignment revocation uses the same assignment row. No Person/binding locks or new Account writes in ADMIN-001, avoiding credential-first versus Person inversion.
3. Through the Academic-owned roster API, acquire the shared enrollment-slot locks described below before taking academic year/period/group or roster row locks; then lock/validate those referenced academic rows and current roster rows in deterministic table/UUID order. The tenant roster mutation/revision namespace in step 1 also fences absent roster rows. DB unique constraints remain the final duplicate defense. All roster writers use this coordinator/order; enrollment rows alone cannot fence an initially empty slot.
4. Recompute request digest and lookup receipt; current authorization precedes replay disclosure. For new requests, reject stale preview before any effect; apply all accepted rows plus protected history and one receipt atomically. Any validation/conflict/audit/DB failure rolls back the entire file. UNCHANGED rows produce no new logical Student/version; receipt may record a whole-import NO_OP without duplication.
5. Commit and return minimal counts/row references/audit receipt. No auto transaction retry after deadlock/timeout, no success returned before commit, no HTTP retry that creates a new key. Database error projection is bounded, without raw identifiers/SQL/PII. A lost ACK is recovered using the same request key after fresh authorization.

**Exact shared enrollment fence (targeted contract correction):** both the existing `ensureStudentEnrollment` writer and roster confirmation must acquire the same transaction-level PostgreSQL advisory lock key, `ac_enrollment:<tenant>:<membership>:<period>`, using the existing `hashtext(key)` single-key advisory namespace. The existing writer already executes `SELECT pg_advisory_xact_lock(hashtext($1))` before its enrollment SELECT/INSERT in [Academic provisioning](../../../runtime/academic-core/src/provisioning.ts); its caller-owned transaction retains that lock until COMMIT/ROLLBACK. Preserve that writer's existing transaction, enrollment validation/idempotency/conflict behavior and all assertions; its only additionally approved future change is the shared UUID validation/key canonicalization below. No wrapper or test double may substitute for the real writer in concurrency evidence.

**Frozen shared UUID/key canonicalization:** define one Academic-owned exported pure `enrollmentSlotKey(tenantId, membershipId, academicPeriodId)` helper in `runtime/academic-core/src/provisioning.ts`; both `ensureStudentEnrollment` and the Academic roster writer must call this same helper. All three inputs must be strings matching the existing case-insensitive canonical hyphenated UUID shape, `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$` with the `i` flag. Reject malformed, missing or non-string values before constructing a lock key or performing any mutation; do not silently accept whitespace, braces or another identifier format. Convert each validated component to lowercase, then return exactly `ac_enrollment:<lowercase tenant>:<lowercase membership>:<lowercase period>`. Normalize before key construction, never only in the CLI, after hashing or just on one writer. There is no second lock-key implementation or new advisory namespace. Existing enrollment APIs retain their signatures and owning-domain authority; PostgreSQL UUID/tenant/membership/year/period/group coherence checks remain mandatory. A well-formed but foreign/ambiguous scope is not authorized by normalization and must fail closed without mutation.

`ensureStudentEnrollment` validates/canonicalizes all three components via this helper **before its existing first enrollment-slot lock** and uses the resulting key with `pg_advisory_xact_lock(hashtext($1))`. Roster confirmation uses that identical helper result with `pg_try_advisory_xact_lock(hashtext($1))`. The same lowercased full key, same `hashtext` function and same single-bigint advisory overload therefore select one effective transaction-level lock for uppercase/lowercase/mixed-case representations of the same records. Canonicalized components also drive the owning membership/period lookups and scope comparisons so a string-case difference cannot produce a different authority decision. These changes do not add Person/Account locks, enrollment transfer, role authority, implicit retry or roster-aware behavior to the legacy enrollment writer.

For each affected Person-bound roster record, resolve the membership through the Tenant Access owning lookup using the authoritative bound Person and current tenant; never accept a membership/Person supplied in CSV. Missing or multiple memberships fail closed as REVIEW_REQUIRED before mutation. Capture/recheck the roster binding/revision under the tenant roster namespace and later roster row lock; a changed resolution/revision is an explicit 409 stale_conflict, never an alternate Person or guessed membership. An unbound roster record performs no identity/enrollment effect; it must not acquire a fabricated membership slot.

Build the complete distinct set of `(tenant UUID, membership UUID, academic period UUID)` slots before effects, including every referenced existing **and initially empty** enrollment slot. Normalize UUIDs, sort the resulting full lock keys lexicographically, and acquire in that order **after** step 1 and the session/account/membership/Operator assignment locks of step 2, **before** academic year/period/group and roster row locks. Roster confirmation uses `SELECT pg_try_advisory_xact_lock(hashtext($1))` for these slots: this conflicts with and holds the exact same lock as the existing writer's blocking acquisition. On any false result, return explicit 409 stale_conflict and roll back the complete transaction, releasing already acquired slots; no loop, sleep, partial effect or automatic transaction retry. This is necessary because legacy academic batch imports can retain earlier enrollment slots in file order: sorting only the new roster writer's blocking requests would not by itself eliminate a reverse-order batch cycle. A busy slot is a concurrency refusal, never treated as an empty enrollment or permission to continue.

After **all** required slots are successfully acquired, freshly SELECT current enrollment state under READ COMMITTED and validate tenant/year/period/group coherence; an earlier preview or pre-lock SELECT is not an authority. Re-read even when a slot was initially observed empty. Hold every acquired slot and required row/assignment/revision lock until transaction COMMIT/ROLLBACK. A current enrollment in another group, ambiguous membership/enrollment, changed bound identity or invalid reference returns REVIEW_REQUIRED; stale preview/state returns 409 stale_conflict. Both refusal paths roll back every proposed roster/history/audit-success effect. The existing enrollment writer, with only the approved shared key validation/canonicalization correction, likewise re-reads after obtaining its blocking slot lock and applies its existing idempotent/conflicting-group rules. No new roster-aware behavior is attributed to that legacy writer, and ADMIN-001 never transfers or writes enrollment itself. A later independently authorized academic operation is not a simultaneous roster mutation; no new academic permission is granted by serialization.

New roster fence/resolution/re-read/refusal code remains in row 14 (`runtime/academic-core/src/roster-import.ts`) and row 16 (HTTP coordinator); actual two-writer PostgreSQL evidence remains in row 23 (`runtime/secure-assessment/test/integration/roster-import.test.ts`).
